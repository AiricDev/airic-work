# Airic Work 产品定义与需求（更新版 PRD）

## tl;dr

Airic Work 是以 Operating Model（OM）驱动后台自主执行、以 DecisionRequest 组织人机协作的平台。业务系统通过标准 API 发起执行，唯一任务归属人依据 Decision Context 处理必要判断；平台保存 Session（即 Trajectory）及 DecisionRequest 生命周期记录 Decision Episode，并通过只读 MCP 向使用身份认证 token 的外部 Agent 提供本人可访问的实践记录。

外部业务服务统一经可配置 MCP 连接接入。CertLab 仅是外部服务示例，不是平台组成部分或固定依赖；
平台不内置 CertLab 的对象、工具名或专属流程。下文 CertLab、TestTask/Finding、Assessment 和 `asset.*` 的场景仅说明一种外部业务实践，
服务的工具 Schema 与能力来自 MCP，业务解释由对应 OM/Skill 和 Agent 承担。

产品包含两项关键方法资产：**OME Skill** 指导专家与外部 Agent 设计和改进 OM；**Worker Skill** 指导后台 Pi Durable Agent 加载和使用 OM、处理人工消息并推进工作。两者分别服务方法工程和实际执行，不构成持续上下级 Agent 委派。

每个实例只使用一个 OM 仓库，支持配置远端 URL 或已有本地 Git 仓库目录；平台提供文件浏览、全文检索、Git 历史及受控同步。OM 构造、Reflection、验证和修改均在外部完成，通过 GitHub/GitLab Review 与合并采纳。新执行使用配置分支的确认提交，实际启动后固定 Commit SHA；URL 来源确认远端最新，本地来源使用本地已提交版本、只显式同步。


## Goals

### Business Goals

| 目标 | 观察指标 | 目标值 |
| --- | --- | --- |
| 提高工作效率 | 可比工作的人类投入时间、完成周期，以及监督和返工时间 | TBD |
| 保持或改善业务成果质量 | 可比工作在相同验收标准下的通过情况、重大遗漏和返工情况 | TBD |
| 自动化水平和工作质量可持续改进 | 在质量达标、必要人工介入得到保留的前提下，可比工作中因方法不足而产生的人工介入减少，同类错误和返工减少。 | TBD |
| 非侵入式集成业务系统 | 通过标准执行 API、身份认证和 MCP 业务能力接入，无需为每个业务系统开发平台专属逻辑。 | TBD |

不以运行量、聊天量、PR 数量或不完整记录中的出现频率替代实际价值。

### User Goals

* **任务归属人**：将工作委托给 Agent，减少重复劳动和持续监督，把精力集中在需要本人专业判断的事项上；需要介入时，能够快速理解问题、作出判断并推动工作继续；随时了解进展、阻碍和结果，取得符合业务要求的成果。
* **专家与 OM 维护者**：从实际工作中的成功、错误和人工纠正中发现改进机会，验证并改进工作方法，使后续工作表现持续提升。
* **业务系统集成方**：以较低的接入和维护成本，让现有业务系统具备 Agent 执行能力，沿用既有业务规则和管理方式。
* **管理员**：以可控的管理成本支持用户开展工作，确保人员、连接和授权配置清楚、可维护。

### Non-Goals

* **不做通用交互式助手**：聚焦业务系统发起、具有明确目标和授权范围的后台工作，不取代 Codex、Claude Code 等通用交互式 Agent，不重建完整 Harness。
* **不取代业务系统**：业务事实、权限、审批、事务和正式完成条件仍由业务系统管理；通过统一接口和 MCP 接入，不为每个业务系统开发深度定制集成。
* **不以消除全部人工介入为目标**：保留必要的专业判断与授权环节。每个执行只有一位任务归属人，不支持多人抢占或竞争处理 DecisionRequest；DecisionRequest 逐项处理，不提供跨 DecisionRequest 批量作答或批准，业务工作的批量交接由业务系统承接。
* **不建设平台内的方法研发与学习中心**：OM 构造、反思、验证和修改在外部完成；沿用 GitHub/GitLab 的评审与合并流程，不自建 Git 或另设 OM 发布审批流程。
* **不建设结构化 OM 知识管理平台**：每个实例使用一个 OM 仓库，以文件浏览、全文检索和 Git 历史支持使用；不提供多 OM 选择、Decision 语义对象管理、知识关系图或 Knowledge Gap 看板，不引入 embedding 或向量检索。
* **不集中接管外部 Agent 的工作记录**：提供获授权实践记录的只读访问，不强制上传完整外部会话，本版不提供任意外部轨迹导入或学习成果回传服务。
* **不建设自助成员准入流程**：用户由管理员统一管理，本版不支持成员邀请或自助注册。


## User Stories

### 任务归属人

* 作为任务归属人，我希望从业务系统将目标和范围明确的工作委托给 Agent，并在离开页面后由其继续执行，以便减少重复劳动和持续监督。
* 作为任务归属人，我希望按工作分组了解相关执行的进展、产出、阻碍和需要我处理的事项，以便安排自己的工作，无需逐条阅读执行记录。
* 作为任务归属人，我希望 Agent 在需要我介入时，清楚说明待判断的问题、已有依据、缺失信息、可选方案及其影响，以便以较少的信息整理成本作出负责的判断。
* 作为任务归属人，我希望逐项回应判断请求，提供选择、观察、专业结论及必要的条件和限制，以便 Agent 准确理解我的意见，并据此推进相关工作。
* 作为任务归属人，我希望在获得新资料、测试结果或整改反馈后，将文字、文件或业务资料引用交给 Agent，以便继续处理受影响的工作，减少手工整理和重复录入。
* 作为任务归属人，我希望能够补充执行指示或停止后续工作，并了解指示是否生效及已经产生的业务影响，以便在情况变化时保持控制。
* 作为任务归属人，我希望清楚知道 Agent 完成了什么、哪些结果已保存到业务系统、还有哪些事项未完成，以便核验成果并安排后续工作。
* 作为任务归属人，我希望 Agent 在我授权的业务身份和范围内操作，并在授权不足或失效时说明影响及恢复方式，以便放心委托工作。

* 作为任务归属人，我希望后台 Agent 按稳定的 Worker Skill 使用 OM、处理我的回答和补充消息，并在中断后继续原工作，以便无需反复解释平台操作方式和任务上下文。

### 专家与 OM 维护者

* 作为专家，我希望读取获授权的实际判断记录，了解当时的问题、依据、所用方法、人工介入和后续结果，以便分析成功或偏差的原因。
* 作为 OM 维护者，我希望在熟悉的外部工具中，结合实践记录和对照案例修改、验证 OM，以便让方法改进有实际依据，并改善后续工作的效率和质量。
* 作为 OM 维护者，我希望沿用 GitHub/GitLab 的变更评审与合并流程，并能区分历史执行所用版本与当前方法，以便审查改动、追溯影响和解释过去的结果。
* 作为专家与 OM 维护者，我希望按文件名、路径和正文查找指定版本的 OM 内容，以便准确理解和维护实际使用的方法。

* 作为 OM 维护者，我希望使用已有 OME Skill 将业务目标、专家经验和代表案例转化为可运行、可验证的 OM，以便持续维护方法，而无需进入平台内的方法设计流程。

### 业务系统集成方

* 作为集成方，我希望通过统一的执行接口、身份认证和 MCP 业务能力接入 Airic Work，以便以较低的开发和维护成本，为现有业务系统增加 Agent 执行能力。
* 作为集成方，我希望沿用自身的工作分组、业务对象和任务表达，以便接入时保留既有业务模型。
* 作为集成方，我希望业务界面与 Airic Work 工作台使用一致的执行和人工反馈记录，以便用户从不同入口操作时获得一致结果。
* 作为集成方，我希望在网络异常、重试和取消时，能够确认实际执行情况及已产生的业务效果，以便避免重复工作和重复业务操作。

### 管理员

* 作为管理员，我希望管理自动创建的用户、使用资格和管理员权限，以便让适当的人员使用系统，并及时调整其访问资格。
* 作为管理员，我希望集中配置 OM 来源、业务服务连接和外部记录读取策略，并了解配置是否有效，以便稳定支持用户开展工作。
* 作为管理员，我希望清楚区分平台连接配置与映射后的用户身份，以便完成系统接入，同时保持业务操作的权限边界。

## Ontology

本章定义 Airic Work 的核心概念、术语、归属和关系，是后续功能需求与系统设计的共同语义基础。概念不要求与数据库表、API 资源或页面一一对应。

### 1. 用户与身份

Airic Work 沿用集成方的用户身份。所有用户均为成员，其中部分用户具有管理员权限，不另设 Member 实体或独立的发起人角色。

| 术语 | 定义与边界 |
| --- | --- |
| 平台实例（Instance） | 一套独立配置和运行的 Airic Work 服务。本版服务一个组织，配置一个 OM 仓库来源，可连接多个外部业务系统实例 |
| 用户（User） | 通过集成方身份认证、使用 Airic Work 的人。Airic Work 使用集成方提供的 token 获取用户信息，并在首次收到该用户的有效应用端请求时创建对应的本地用户记录，默认获得平台使用资格；用户及管理员权限在 Airic Work 中管理，后续可在用户管理中设置使用资格 |
| 管理员权限 | 部分用户具有的平台管理权限，用于维护实例配置及实施本版允许的用户管理操作。不自动赋予读取其他用户执行内容或代表其他用户开展业务操作的权限 |
| 任务归属人（Execution Owner） | 发起某个 Execution 的用户，也是该执行的唯一归属人。该执行的人工判断请求由其处理，Agent 代表其本人开展业务操作 |
| 身份认证 token | 用于验证用户身份的凭据。来自平台信任的集成方认证来源，通过约定方式取得和核验用户信息；不以 token 字符串本身作为用户的稳定标识 |
| 专家 / OM 维护者 | 在外部环境中分析实践、构造、验证和维护 OM 的人。维护 OM 只需相应 GitHub/GitLab 仓库权限，无需直接使用 Airic Work；需要读取 Trajectory 时，通过身份认证 token 配置外部客户端访问 Airic Work 的只读 MCP |
| 业务系统集成方 | 将业务应用及其认证、业务 MCP 能力接入 Airic Work 的参与方，不作为独立的平台用户角色 |

身份与归属规则：

* 发起执行的用户就是任务归属人，不允许调用方另行指定其他人为归属人。
* 应用端请求、后台 Agent 业务操作及人工回应均关联实际用户；Agent 代表任务归属人执行，不创建独立的 Agent 用户。
* 软件客户端和运行组件属于技术基础设施，不作为另一套业务身份。Session 历史区分用户直接输入和 Agent 操作的来源。
* 本地 User 是集成方用户在 Airic Work 中的对应记录，不建立另一套独立注册和密码身份。
* 用户以“可信认证来源 + 稳定用户标识”识别，不凭姓名或邮箱合并身份。
* 业务身份映射统一承接用户认证和访问资格，不另建业务委托、业务权限或外部读取授权体系；管理员权限和本地用户使用资格由 Airic Work 管理。
* Git 仓库权限不自动赋予 Airic Work 记录读取权限；外部 Agent 使用身份认证 token，按与工作台相同的用户访问规则读取。

### 2. 工作组织与执行

| 术语 | 定义与边界 |
| --- | --- |
| 业务系统 / 业务系统实例 | 提供业务事实和受控业务能力的外部应用及其具体部署，拥有自身的数据、权限、业务流程和正式完成条件 |
| 业务任务（Business Task） | 由业务系统定义和管理的工作，可以是较大的整体工作。Airic Work 不接管其生命周期或正式完成状态 |
| 工作分组（Project） | 调用方定义、由 Airic Work 管理的执行分组，用于组织相关 Execution。它可以对应业务任务或其他业务分组，不承担业务完成判定、自动调度或结果合并 |
| 执行（Execution） | 用户通过业务应用发起、由 Airic Work 管理的一次 Agent 执行。具有唯一归属人，记录输入、实际执行版本、进展及执行轨迹，可以完成业务任务中的一部分工作 |
| 业务上下文输入（`task`） | 创建 Execution 时提交的自定义 JSON 对象，承载业务任务或对象的标识与属性。它是创建时的输入快照，不是业务事实的权威存储 |
| 执行指令（`instruction`） | 创建 Execution 时提交的自然语言说明，表达本次执行承担的工作、范围、预期动作及必要限制。业务任务在多个 Execution 之间的具体分工由此描述 |
| 执行轨迹（Trajectory） | Execution 对应的 Session，是同一个运行记录对象的另一种称呼，不另建轨迹实体 |

关系与边界：

* 每个 Execution 归属一个 Project，且只有一位任务归属人；一个 Project 可以组织多个 Execution。
* 一项业务任务可以关联多个 Execution，分别承担其中一部分工作。平台不据此建立子任务分解、依赖调度或自动汇总完成机制。
* Project 是执行分组，业务任务是业务义务，两者不要求一一对应。
* Project 的外部身份由“业务系统实例 + 调用方 `project_id`”确定；显示名称不参与身份识别。
* 业务任务标识用于关联同一业务工作，创建幂等标识用于识别同一次创建操作，不能互相替代。
* Execution 可以包含多轮模型调用、工具操作、人工反馈和恢复过程，不等同于一次对话或一次模型调用。
* Agent 通过 MCP 在业务系统中实施操作，形成或更新业务记录。业务系统拥有这些业务事实，Airic Work 在 Trajectory 中记录相关动作、返回、引用及结果确认情况。
* Airic Work 不另设 Execution Result 或业务产出实体。执行页面可依据执行记录提供进展、完成说明、未完成事项和业务记录链接。
* Execution 结束不等于业务任务正式完成；工具调用发起、业务操作成功及业务正式确认分别记录，不相互替代。

### 3. 判断与人机协作

Airic Work 以 DecisionRequest 组织需要用户介入的判断。用户提交 UserDecision 后，平台将其组装为消息交给 Agent，由 Agent 结合 OM 和当前工作情况继续执行。平台不另设判断采纳或问题解决的业务状态机。

| 术语 | 定义与边界 |
| --- | --- |
| DecisionRequest | Agent 在某个 Execution 中，围绕一个具体问题向任务归属人发出的人工介入请求。可以请求用户作出选择、提供专业结论、补充事实或说明授权范围，不等同于业务审批或待开展的业务工作 |
| Decision Context | 理解和回应某个 DecisionRequest 所需的信息，包括问题及触发原因、相关事实、规则、来源版本、既往决定、缺失信息、不确定性、可选方案及其影响。相关文件和记录作为其中的信息或来源引用，不另设 Evidence 实体 |
| Decision Brief | 面向用户呈现 Decision Context 的交互形式，帮助用户理解问题、查看依据并提交 UserDecision。不作为独立业务实体，也不建立独立生命周期 |
| UserDecision | 任务归属人针对某个 DecisionRequest 提交的一次回应，包括所选选项、补充文字及可选附件，可以表达判断、观察、事实、条件或限制。每次提交保留固定内容、提交人、时间及来源关联 |
| Decision Episode | 一个 DecisionRequest 的完整生命周期记录，从创建、向用户展示到用户提交 UserDecision，并关联消息交付及后续执行历史。与 DecisionRequest 一一对应，不自动成为正确知识或正式 Precedent |

关系与协作规则：

* 一个 Execution 可以产生零个或多个 DecisionRequest。每个 DecisionRequest 属于一个 Execution，由该 Execution 的任务归属人逐项处理。
* DecisionRequest 总是需要任务归属人回应。界面展示 Decision Brief，并以选项卡、文本框及文件上传等控件收集 UserDecision；UserDecision 提交成功即标记为已回答。补充或更正保留历史，不因 Agent 仍需信息而撤销已回答事实；进一步提问可新建 DecisionRequest。
* 每条 UserDecision 关联用户回应时查看的 Decision Context 版本，后续资料更新不改写原始提交。
* 平台保存 UserDecision，并将其组装成消息交付对应 Execution 的 Agent。保存成功、消息交付和 Agent 实际继续执行是不同事实。
* 平台不把提交 UserDecision 自动解释为业务批准、问题已解决或业务工作已完成。Agent 依据消息内容、OM 和当前情况决定后续动作，必要时进一步询问。
* 每个 DecisionRequest 对应一个 Decision Episode，两者同时建立关联；Decision Episode 引用相关 Session 消息、Decision Context 和 UserDecision，不独立划分判断片段。
* DecisionRequest 已回答与消息已交付、Agent 已继续执行分别记录，不以执行结果决定是否已回答。

### 4. 执行消息

Steering Input 是任务归属人在 DecisionRequest 流程之外向 Agent 发送任意工作消息的入口。

| 术语 | 定义与边界 |
| --- | --- |
| Steering Input | 任务归属人向某个 Execution 提交的消息，可以包含文字、文件或业务资料引用，用于补充指示、提供新信息、询问情况或要求调整工作。它不要求关联 DecisionRequest |

* 一个 Execution 可以接收多条 Steering Input。平台记录提交内容、提交人、时间及附件，并交付对应 Agent。
* UserDecision 是对特定 DecisionRequest 的结构化回应；Steering Input 是面向 Execution 的一般消息。两者均通过消息交付 Agent，但保留各自的来源和关联。
* Agent 可以从 Steering Input 中理解与待处理问题有关的信息，但平台不将其自动转换为 UserDecision。
* 消息内容不扩大用户授权，也不绕过业务系统规则。
* Execution 结束后仍可接收 Steering Input 或 UserDecision，并在原 Execution 中继续执行，沿用同一个 Session、Workspace 和已固定的 OM 版本。消息协调与交付失败恢复机制在运行设计中明确。


### 5. 方法与知识

Airic Work 将 OM 作为版本化文件使用，不将其内部知识提取为平台独立管理的语义对象。

| 术语 | 定义与边界 |
| --- | --- |
| Operating Model（OM） | Agent 开展某类工作所需的方法知识，包括工作目标、约束、判断方法、信息依赖、结果要求及领域能力依赖。通过 Git 仓库管理和交付 |
| Root OM | OM 的运行入口，说明工作范围、执行原则、知识路由和能力依赖。执行时常驻加载，其他相关知识按需加载 |
| Decision Model | OM 中针对一类可重复出现的问题组织的判断知识，包括适用条件、所需信息、判断方法及可能结果。OM 文件中的 Decision 指该概念，与 DecisionRequest、UserDecision 和 Decision Episode 分别表达 |
| Precedent | 经验证与采纳、可在明确适用边界内供后续判断参考的案例知识。Decision Episode 不自动成为 Precedent |
| Knowledge Gap | 已识别的方法知识不足或不确定性。与某次执行缺少业务事实、文件、工具或授权分别表达 |
| Skill | 指导 Agent 开展某类活动的行为方法。可以指导 OM 的构造或执行，但不授予权限，也不代替业务系统规则 |
| OME Skill | 指导专家与外部 Agent 开展 OM Engineering 的方法入口，负责构造、评审、验证和持续改进 OM。沿用 `.agents/skills/operating-model-design/` 中的现有初稿 |
| Worker Skill | 指导后台 Pi Durable Agent 如何在 Airic Work 中开展工作的执行方法，包括理解任务、使用 OM、取得 Decision Context、调用工具及处理人机消息；与 Agent 运行环境配套设计 |
| OM Engineering（OME） | 在外部环境中构造、评审、验证和改进 OM 的活动，成果通过 Git 仓库交付 |
| Reflective Learning | 基于实践记录开展反思、归因、提出改进并验证效果的活动。在外部环境开展，不由 Airic Work 建立内部管理流程 |

版本与交付规则：

* OM 文件及其修订以 Git 仓库为权威来源，评审与采纳沿用 GitHub/GitLab 的变更流程。
* 每个 Execution 启动时固定使用已确认的 OM Commit SHA；后续同步不改变进行中或历史执行的方法版本。
* URL 来源由平台 clone 并确认远端分支；本地目录直接复用 Git 仓库，使用配置分支的已提交版本，不加载未提交修改、不自动拉取。没有 remote 也能运行、浏览和检索，只禁用同步并提示；本轮不支持无 Git 的普通目录。
* Decision Model、Precedent 和 Knowledge Gap 可以在 OM 文件中表达，不因此产生独立的平台实体、管理页面或生命周期。
* `.ome/` 是 OM 维护者本地的方法工程工作目录，不提交 Git，不由 Airic Work 同步、检索或加载。
* 交付的 OM 应包含执行所需知识，不得依赖 `.ome/` 中的本地文件才能理解或运行。

### 6. 执行历史

Airic Work 保存每个 Execution 对应的 Agent Session 历史，用于查看执行过程、恢复工作，以及为 Decision Episode 提供原始记录。

| 术语 | 定义与边界 |
| --- | --- |
| Session（Trajectory） | Execution 对应的 Agent 会话与持久化运行历史；Trajectory 是它的另一种称呼。一个 Execution 对应一个 Session，继续执行时沿用，不另建轨迹对象 |

记录规则：

* Session 保留消息和操作的来源、时间及必要关联，能够区分用户输入、Agent 操作和工具返回。
* DecisionRequest、UserDecision 和 Steering Input 与对应的 Session 消息关联；Decision Episode 引用相关历史记录，不重复保存一套执行过程。
* 工具调用发起与返回结果分别保留；尚未确认的业务效果不能记录为成功。
* 历史记录缺失、压缩、清理或不可访问时，明确说明覆盖限制。
* Execution 记录实际使用的 OM 仓库来源和 Commit SHA，历史查看不改变该版本。
* 不另设 Trajectory Event 或 Audit Record 业务实体。

### 7. Workspace 与文件

| 术语 | 定义与边界 |
| --- | --- |
| Workspace | 每个 Execution 独立拥有的 Agent 文件空间，用于读取用户上传文件、保存和处理工作文件。等待、恢复及结束后继续执行均沿用；不同 Execution 不自动共享文件 |
| 上传文件（Uploaded File） | 用户通过 UserDecision 或 Steering Input 提交给 Agent 的文件。文件关联对应输入，并交付到 Agent 可访问的 Workspace |

文件交付规则：

* UserDecision 和 Steering Input 均支持上传一个或多个文件，也支持仅提交文字。
* 平台保留已提交输入与具体文件内容的关联，确保 Agent 读取的是用户提交的文件。
* 文件上传成功、交付到 Workspace 和 Agent 实际读取是不同事实；交付或读取失败时应明确说明。
* Workspace 中的文件在执行等待和恢复期间应保持可用；隔离、保留和清理规则在运行设计中明确。
* Agent 通过业务 MCP 获取或提交文件时，遵循该服务的工具合同。Airic Work 不定义业务资料、业务修订或业务效果实体。

### 8. 运行、连接与身份

| 术语 | 定义与边界 |
| --- | --- |
| Runtime / Harness | 提供 Agent 模型调用、消息处理、工具执行、Session 持久化与恢复等能力的运行基础 |
| MCP 连接 | Airic Work 访问外部服务的连接配置。可用工具及操作合同由对应 MCP 服务提供，业务含义由 OM、Skill 和 Agent 理解 |
| 业务身份映射 | Airic Work 根据可信集成方 token 获取用户信息，建立与本地 User 的稳定对应关系，并据此确定执行归属和访问资格。后台业务调用使用该用户身份，不另建业务委托或业务权限模型 |
| Airic Work MCP | 向外部 Agent 提供执行历史及 Decision Episode 的只读访问入口。使用身份认证 token 识别用户，按与工作台一致的用户访问规则提供内容，不另设外部授权体系 |

平台接受的 token 来源、用户识别方式及后台调用时如何使用该身份，在集成合同中明确。token 不进入模型消息、Session 历史或普通 Workspace 文件。

### 9. 外部业务概念与术语约束

CertLab、Assessment、TestTask、Finding 和业务资料修订等属于外部业务系统的概念。Airic Work 可以通过 MCP 操作并引用这些对象，但不将其固化为通用平台实体。

本文统一使用：

* **Execution** 表示平台管理的执行，避免用“任务”同时指代业务义务和技术执行。
* **Decision Model** 表示可复用判断知识，**DecisionRequest** 表示需要用户回应的人工协作请求，**Decision Episode** 表示一个 DecisionRequest 的生命周期记录。
* **UserDecision** 表示对 DecisionRequest 的一次用户回应，**Steering Input** 表示面向 Execution 的补充输入。
* **执行结果**与**业务正式完成**分别表达。
* **来源引用**与**内容访问权**分别表达。

### 10. 核心关系与生命周期约定

* 发起 Execution 的 User 即唯一任务归属人；用户首次通过集成方 token 认证后自动创建本地记录并获得使用资格，后续由 Airic Work 用户管理维护。
* 一个 Project 包含多个 Execution；同一业务任务可以由多个 Execution 分别完成一部分，具体分工用 `instruction` 自然语言描述。
* 一个 Execution 对应一个 Session（即 Trajectory）和一个独立 Workspace，并记录固定 OM 来源及 Commit SHA。
* 一个 Execution 可以包含多个 DecisionRequest；一个 DecisionRequest 对应一个 Decision Episode，UserDecision 提交成功即已回答。
* UserDecision 和 Steering Input 均作为消息交付 Agent；Execution 结束后收到新消息可以在原 Execution 中继续执行。
* 本章所列概念边界已确定。具体接口、消息交付与重试、存储、保留和清理机制在后续设计中落实。

## Skill 体系与系统关系

OME Skill 和 Worker Skill 是产品交付与演进的一部分，不只是文档中的泛称。它们与领域 OM、平台和 Runtime 各自承担不同职责。

| 维度 | OME Skill | Worker Skill |
| --- | --- | --- |
| 解决的问题 | 怎样把业务目标、专业经验和案例整理成可复用、可验证的方法 | 后台 Agent 怎样在平台中使用这些方法完成被委托的工作 |
| 使用者与环境 | 专家与 OM 维护者在外部 Agent 环境使用 | 承担 Execution 的后台 Pi Durable Agent 使用 |
| 主要输入 | 工作目标、业务能力合同、专家经验、代表案例、已有 OM；改进时可读取获准的 Session 和 Decision Episode | 当前 Execution 的 `task`、`instruction`、固定版 OM、UserDecision、Steering Input、Workspace 文件和工具能力 |
| 主要产出 | Root OM、Decision Model 等运行时知识，以及作者侧候选、案例和验证记录；采纳的方法变更经 Git Review 合并 | Agent 消息、DecisionRequest、业务 MCP 调用及其结果，保留在原 Execution 的 Session 与 Workspace 中 |
| 与平台的关系 | 平台提供 OM 文件浏览及实践记录读取；方法设计与反思在外部完成，不增加内部学习中心 | 平台装配执行方法并提供受控能力，维护用户身份、输入提交与交付、执行控制及历史 |
| 当前状态 | 已有 [operating-model-design 初稿](../.agents/skills/operating-model-design/SKILL.md)，作为后续维护基础；存在初稿不等于所有业务场景已经验证 | 已有 [Worker Skill v0.1.0 初稿](../backend/skills/airic-work-worker/SKILL.md) 及配套[运行环境设计](worker-runtime-design.md)；真实 Agent 行为、装配与恢复能力仍待验证 |

关键关系与边界：

* **OME Skill 定义如何设计方法，OM 表达具体领域的方法，Worker Skill 定义如何执行工作。** Worker Skill 包含通用的平台工作约定，领域判据和知识路由由固定版 OM 提供，不把某个业务系统的流程固化进通用 Worker Skill。
* **运行环境提供真实能力。** Session 持久化、Workspace、文件处理、MCP、消息接收、运行停止与恢复由 Runtime 和宿主兑现。Worker Skill 指导如何使用这些能力，不能以文字替代尚不存在的工具、权限或可靠交付机制。
* **Root OM 是领域常驻入口，Worker Skill 是执行行为入口。** 执行时两者都需实际装配；仅把文件放进仓库不等于 Agent 已读取。具体装配机制及冲突提示由后续运行环境设计落实。
* **外部方法改进通过 Git 影响未来执行。** 专家使用 OME Skill 产出 OM 变更，经既有 Review 合并后由平台同步；Worker Skill 不自动运行 OME、修改 OM 或将 UserDecision/Decision Episode 升级为 Precedent。
* **版本分别记录。** Execution 记录实际 OM Commit SHA、Worker Skill 与 Runtime 版本；同一执行继续时沿用已记录版本。OME Skill 的版本和验证依据属于方法作者侧记录，不要求后台加载作者过程。
* **沿用现有概念。** Worker Skill 不是新的用户角色、业务 Worker 实体或多 Agent 任务树，也不是负责消息派发的技术 worker；它不改变已确定的 Execution、Session、DecisionRequest 关系。

## Functional Requirements

本章将 Ontology 中确定的概念转化为可观察、可验收的系统行为。需求按用户接入、工作委托、后台执行、人工协作和实践读取组织。P0 为核心闭环，P1 为管理与使用体验；优先级不代表已经实现。对象关系以 Ontology 为准，接口、存储和运行机制由后续设计落实。

### 1. 用户接入与使用资格（P0）

* **身份识别**：应用端使用集成方 token 访问 Airic Work。平台获取用户信息，以“可信认证来源 + 稳定用户标识”定位 User，不凭姓名或邮箱自动合并用户。
* **首次接入**：首次有效请求自动创建本地 User 并获得使用资格；再次请求关联已有 User，不重复建人，也不因重新认证恢复已停用用户。
* **执行归属**：发起 Execution 的用户就是唯一任务归属人。平台从已验证的身份确定归属，不接受通过 `task`、`instruction` 或任意 `userId` 指定其他归属人。
* **统一身份**：工作台、标准 API 和 Airic Work MCP 使用同一用户识别及访问规则；后台 Agent 通过业务 MCP 使用任务归属人的身份，不创建独立技术用户或回退到共享、管理员身份。
* **访问范围**：用户只能查看和操作本人 Execution 及相关 DecisionRequest、UserDecision、Steering Input、Session 和文件。Project 列表与数量仅反映本人可见执行；管理员权限不自动赋予他人内容访问权。
* **失效处理**：token 无效、用户停用或外部服务拒绝操作时，明确显示原因和受影响工作，不伪报成功。重新取得有效身份后在原执行中恢复，不更换归属人或改写历史。
* **凭据处理**：token 由运行基础设施处理，不进入模型消息、OM、普通 Workspace 或 Session 历史。不另建业务委托、业务权限或外部读取授权体系。

### 2. Project 与 Execution 创建（P0）

业务系统通过标准 API 委托工作，工作台与业务系统使用相同应用服务和记录。没有通用手工新建 Execution 入口。

#### 创建输入

| 输入 | 要求 |
| --- | --- |
| `project_id` | 必填，调用方提供的稳定工作分组标识；以“业务系统实例 + `project_id`”确定 Project 身份 |
| `project_name` | 必填，工作分组显示名称，用于首次创建 Project，不参与身份识别 |
| `task` | 调用方自定义 JSON 对象，承载业务关联与上下文；可用 `id` 表达业务任务标识，其余结构由调用方定义 |
| `instruction` | 必填的非空自然语言，描述本次执行的目标、分工、范围、预期工作及必要限制 |

token 与创建幂等键由接入合同承载，不放入自定义业务属性。业务系统实例从可信接入上下文取得，不从 `task` 推断。

```json
{
  "project_id": "order-2026-0042",
  "project_name": "华东工厂设备采购",
  "task": {
    "id": "delivery-review-008",
    "type": "delivery_review",
    "attributes": {
      "order_id": "PO-0042",
      "delivery_id": "DEL-008",
      "document_revision": 3
    }
  },
  "instruction": "负责检查本次交付材料是否齐全，列出缺失项及其影响，并将检查结果登记到采购系统。涉及例外接受时提交人工判断。"
}
```

示例中的 `type`、`attributes` 及其内部字段不属于平台强制 Schema。

* **按需建组**：创建执行时查找对应 Project，不存在则创建，无需集成方先调用独立建组接口。返回内部 Project/Execution ID 及原始分组标识，明确区分。
* **分组查看**：按 Project 展示本人可见 Execution 的进展与待回答事项；Project 不持有业务完成状态，不自动调度、合并成果或判定整体完成。
* **分工表达**：同一业务任务允许创建多个 Execution，分别完成一部分；分工通过 `instruction` 表达，不新增平台子任务或执行依赖模型，不自动共享消息和文件。
* **创建幂等**：同一创建键和相同输入返回原 Execution，同键不同输入报冲突。网络重试沿用原键；有意创建另一次执行使用新键。`project_id` 和 `task.id` 不代替创建幂等键。
* **输入留存**：保存原始 `project_id`、`project_name`、`task` 和 `instruction`，后续业务对象变化不覆盖创建快照。专业含义交给 OM、Agent 和业务工具解释，不形成平台业务 Task 生命周期。

### 3. Execution 运行、停止与继续（P0）

* **启动准备**：为 Execution 关联唯一 Session 和独立 Workspace；首次实际启动前确认实例 OM 来源分支的最新提交，记录仓库来源与 Commit SHA。无法确认时明确阻碍，不静默用旧缓存启动。
* **后台执行**：Agent 结合 `instruction`、`task` 和固定版 OM 推进工作，页面关闭不停止后台执行。Pi Durable 为目标 Runtime，具体能力以实际接入验证为准。
* **业务操作**：业务服务通过可配置 MCP 提供工具。Agent 根据工具合同和 OM 查找信息、处理文件、实施操作；不要求平台内置某个业务系统的对象、工具名或专属适配器。
* **增量推进**：已有信息足以开展的工作先执行，不统一要求全部资料齐全。缺少信息或需要用户判断时提出 DecisionRequest，等待期间可继续无依赖工作。
* **进展呈现**：用户可查看当前进展、阻碍、待回答 DecisionRequest、执行说明及 Session 中的业务操作和链接。平台不另建 Execution Result 或业务产出实体；执行结束不宣称业务任务正式完成。
* **取消执行**：提供请求取消入口，分别呈现请求已接受和实际停止；停止后续工作，不回滚已发生的业务效果。
* **消息续行**：Execution 结束后收到 UserDecision 或 Steering Input，可以继续原 Execution，沿用同一 Session、Workspace、用户归属及固定 OM 版本，不自动新建执行或切换到最新 OM。
* **异常恢复**：中断后保留已提交输入和可用执行历史，恢复时不丢失待交付消息；可能产生业务效果的操作按对应 MCP 合同核验后再决定重试，不盲目重放。

### 4. DecisionRequest 与 UserDecision（P0）

#### 创建与展示

* Agent 围绕一个具体问题创建 DecisionRequest，关联当前 Execution；每个 DecisionRequest 总是需要任务归属人回应，不用它记录普通进展或自主完成的每个业务动作。
* 面向用户提供待回答 DecisionRequest 列表及执行内入口，逐项查看和处理，不支持跨 DecisionRequest 批量作答或批准；通知已读不算已回答。
* 通过 Decision Brief 呈现 Decision Context：说明问题、触发原因、已知事实、信息依赖、缺失及其影响、可选方案、建议理由、风险和不确定性，使用户无需通读 Session 即可回应。
* 提供选项卡、文本框和可选文件上传。选项说明含义及预期动作，Agent 可以推荐但不替用户预选或提交；允许用户用文字补充条件、事实或其他处理意见。
* Decision Context 中的来源引用尽可能提供系统、对象标识、版本及位置，支持查看可访问原文。不可读取或依据不完整时明确限制，不用摘要冒充已读原件，不另建 Evidence 实体。

#### 回答与消息交付

* 用户提交选择、文字及可选附件形成 UserDecision。可以仅提交有实质内容的文字，不统一强制附件或完整推理；适用业务方法要求的信息由 Agent 和 OM 说明。
* UserDecision 保存成功即将 DecisionRequest 标记为已回答。该行为不取决于 Agent 是否认为信息充分、是否已收到消息或业务操作是否成功。
* 每次提交固定保存内容、提交人、时间、附件及所查看的 Decision Context 版本。用户可以补充或更正，保留原内容与更正关联，不静默覆盖历史。
* UserDecision 组装为消息交给对应 Execution 的 Agent，保留其 DecisionRequest 关联。平台分别显示已提交、消息交付和实际继续情况，不建立额外的采纳或解决状态机。
* 重试不重复保存同一提交或重复投递同一消息；同键异内容拒绝。消息交付失败可重试，不撤销已保存的回答。
* Decision Context 来源变化不清空用户草稿、不改写或撤销已提交 UserDecision；后续是否复核由 Agent 依据 OM 判断。需要新的用户回答时新建 DecisionRequest，不把原记录恢复为待回答。
* 保留用户输入和 Agent 解释的区别，未知理由如实标记；UserDecision 不替代业务正式审批，也不自动代表业务工作完成。

### 5. Decision Episode 查看（P0）

* 创建 DecisionRequest 时同时建立一一对应的 Decision Episode 关联；Decision Episode 展示该 DecisionRequest 从创建、向用户展示、提交 UserDecision 到消息交付的生命周期，并链接后续执行记录。
* 用户能够从 DecisionRequest 或 Session 定位 Decision Episode，查看当时的 Decision Context、UserDecision 及更正、相关时间、文件关联和对应 Session 消息。
* 所用 OM 版本从 Execution 关联取得，不建立另一套方法版本。生命周期事实来自 DecisionRequest、UserDecision 和 Session，不要求 Agent 事后独立提取判断片段。
* 已回答状态与 Agent 继续执行情况分别显示；缺失、清理、脱敏和不可访问的内容明确说明。
* Decision Episode 不自动成为 Precedent，不提供平台内反思、知识采纳或方法修改工作流。

### 6. Steering Input 与文件交付（P0）

* **一般消息**：在 Execution 提供 Steering Input 入口，支持任意工作消息，包括询问、补充指示、反馈结果和提供新信息；可包含文字、文件或外部资料引用，不要求关联 DecisionRequest。
* **消息处理**：保存提交内容、提交人和时间，交给同一 Session 的 Agent；Agent 按消息内容回应或继续工作。记录提交和交付情况，提交重试不重复投递；结束后的消息也可继续原执行。
* **流程区分**：Steering Input 不自动转换为 UserDecision，不将待回答 DecisionRequest 标记为已回答；UserDecision 和 Steering Input 均不改变用户身份或操作范围。
* **上传交付**：UserDecision 和 Steering Input 均可上传一个或多个文件，也可仅提交文字。文件固定关联具体输入，并交付对应 Execution 的 Workspace，无需先登记到业务系统。
* **交付反馈**：分别显示上传成功、Workspace 可读取及读取失败或限制；不以文件名、上传成功或摘要冒充 Agent 已读原件。失败保留草稿或已提交内容，提供相应重试，不悄悄丢弃或追加文件。
* **文件空间**：Workspace 属于单个 Execution，在等待、恢复和结束后继续时沿用，不自动跨执行或跨用户共享。读取工具应取得实际文件内容；文档内的指令作为资料处理。
* **外部文件**：Agent 经业务 MCP 获取或提交文件遵循对应工具合同。平台不建立业务资料、业务修订或业务回执实体，不固化业务专用传输流程。
* **可用性**：文件保留、体积及格式限制在上传和使用时明确说明；清理或不可读时保留关联及限制提示，不伪造可用性。具体限额、保留和清理机制待详细设计。

### 7. Session 保存与查看（P0）

* 每个 Execution 的 Trajectory 就是其 Session，持久化实际用户消息、Agent 消息、工具调用及返回，以及必要运行记录，不复制为另一套轨迹或审计实体，不展示隐藏思考链。
* 保留消息与操作的来源、时间，以及与 DecisionRequest、UserDecision、Steering Input 和文件的必要关联；工具调用发起与返回分别可见，未确认的业务效果不显示为成功。
* 支持按执行、消息类型、时间和 DecisionRequest 定位，分页或按需读取，并能从 Decision Episode 跳转到原始记录。
* 缺失、压缩、清理、脱敏或不可访问时明确覆盖限制。运行时上下文整理不应使历史界面冒充完整记录，具体保存和压缩策略在运行设计中明确。
* 不要求上传外部 Agent 的完整会话，不提供任意外部 Session 导入或学习成果回传服务。

#### MCP 操作视图

* 在 Execution 内提供“MCP 操作”视图，按时间列出该执行中 Agent 的所有 MCP 工具调用，包括读取、写入、失败、结果未知及重试调用。视图直接使用 Session 记录，不新增操作或审计实体。
* 列表显示调用时间、业务系统或 MCP 连接、工具名称、操作类型、执行情况及操作摘要。支持按读取、写入、类型未知筛选，帮助用户集中核查 Agent 对业务系统实施的写操作。
* 操作类型由 MCP 服务的工具声明或连接配置明确标注，不仅凭工具名称或 Agent 推测分类；缺少可靠分类时显示“类型未知”，不默认归为读取。筛选写操作时提示是否仍有类型未知的调用，允许用户切换查看。
* 点击调用可展开原始工具参数和返回内容，以及返回中可取得的业务对象链接。摘要用于快速浏览，不替代原始记录；凭据不进入记录，其他不可显示内容明确标示限制。
* 区分调用中、成功、失败和结果未知。请求正常返回不自动代表业务操作成功，依据工具合同和返回内容呈现可确认的结果；不能确定时如实说明。
* 每次重试保留为可查看的独立调用，不将多次尝试合并成一次成功操作；能够区分原调用及其重试，避免把调用次数直接解释为业务效果数量。
* 支持从调用定位原始 Session 消息；存在已记录的 DecisionRequest/UserDecision 关联时，可从 Decision Episode 查看后续相关调用，也可从调用返回相关 Decision Episode，不推测或补造因果关系。

### 8. OM 文件、版本与执行加载（P0）

* **唯一来源**：管理员配置一个 Git 仓库和来源分支，所有 Project/Execution 共用。不提供多 OM 列表、项目级 OM 选择器或平台内 OM 创建流程。
* **来源方式与同步能力**：URL 创建受管仓库，本地 Git 目录直接复用并识别 remote。本地仅显式同步；没有可用 remote 时禁用同步并说明原因，不阻止使用本地提交。有多个 remote 且无法明确选择时提示配置，不任意选择。同步不覆盖本地修改、不自动切换分支或强制重置。
* **文件浏览**：展示已同步提交的目录、Markdown/文本内容，支持打开指定文件；展示提交历史、提交信息、变更文件和 diff，并可跳转 GitHub/GitLab。
* **全文搜索**：按文件名、路径和正文关键词搜索，结果显示路径、片段和命中位置；范围固定当前选定快照，显示来源与 SHA，不跨版本混合。提供清空、无结果和失败状态，不引入向量检索。
* **固定版本**：新执行实际启动时按来源方式确认提交并在 Execution 保存来源及 SHA；URL 确认远端最新，本地确认配置分支的本地提交。同步新提交、切换浏览版本或继续旧执行不改变原执行版本，历史来源不可被配置变更覆盖。
* **方法加载**：后台加载固定提交的 Root OM，以根 `om.md` 或明确配置入口常驻，按需加载相关 Decision Model 和知识。保留实际加载文件及 Skill/Runtime 版本记录；仓库同步不代表方法已经装配。
* **作者边界**：`.ome/` 只存在于维护者本地，不提交 Git，不由平台同步、浏览、搜索或加载。运行时引用缺失或越界时明确报告，不回退到本地作者材料。
* **知识表达**：Decision Model、Precedent、Knowledge Gap 均按文件内容处理，不建立语义索引、关系图或独立治理页面。
* **异常反馈**：OM 未配置时引导管理员配置；URL 来源同步失败时可查看已保存历史，但不能冒充已确认最新。本地来源的 remote 缺失或同步失败不阻断使用有效本地提交，明确区分“同步能力”与“本地可运行”。切换仓库来源不改写旧执行记录，历史保留和恢复机制需详细设计。
* **方法维护**：OME 和 Reflective Learning 在专家的外部环境开展，维护者通过 Git Review 修改并采纳 OM。Airic Work 只同步文件及提供实践记录；后台 Worker Skill 负责使用 OM、取得信息、调用工具、提出 DecisionRequest 和处理消息，具体要求见本章第 11 节。

### 9. Airic Work MCP 只读访问（P0）

* 外部 Agent 使用身份认证 token 访问，按与工作台一致的 User 使用资格和内容范围定位 Execution、分页读取 Session、读取 Decision Episode 及相关 Decision Context 和版本引用。
* Git 仓库权限仅支持 OM 维护，不自动提供执行记录访问。平台不为外部客户端增设独立用户角色、业务委托或授权审批流程。
* MCP 只提供读取，不能创建或取消执行、提交 UserDecision、发送 Steering Input、修改 OM、重放业务动作或读取 token。
* 读取记录与工作台采用相同的缺失和脱敏说明。来源引用不自动带出业务原文或附件；不交付不可访问内容，不建立第二份 Session。
* 用户停用或身份失效后拒绝后续读取，不因分页游标、缓存或知道记录标识绕过校验。正式工具名、传输方式及分页合同待详细设计。

### 10. 用户管理与实例设置（权限保护 P0；管理体验 P1）

* **用户管理**：在 Airic Work 查看和维护自动创建的 User，搜索用户，按启用状态及管理员权限筛选，设置使用资格和管理员权限。用户均为成员，不建立独立 Member 对象、邀请或密码注册流程。
* **停用保护**：停用不删除历史或修改执行归属；重新认证不绕过停用。禁止停用自身、停用或降级最后有效管理员；有未交接执行或待回答 DecisionRequest 时保留原有责任保护，不引入转派机制。
* **实例设置**：集中配置组织/时区、集成方认证、唯一 OM Git 来源、业务 MCP 连接、Runtime 能力和版本，以及文件和记录保留策略；提供标准 API 与 Airic Work MCP 接入说明。
* **配置反馈**：技术测试、保存成功和实际生效分别展示，失败保留输入。配置变更不静默替换运行中 Execution 的用户或 OM 版本；不明确的历史和运行影响在变更前说明。
* **个人设置**：支持显示名、语言/时区，以及待回答 DecisionRequest、执行异常和更新的站内提示；提示已读与实际回答分别记录。

### 11. OME Skill 与 Worker Skill（P0）

* **OME 方法入口**：维护和演进现有 `operating-model-design` Skill 初稿，不另建一套平行 OME 方法。支持专家在外部环境构造、评审、验证和改进 OM；作者侧 `.ome/` 保留本地，不进入交付的运行时知识。
* **OM 的可执行交付**：OME Skill 指导维护者明确 Root 入口、知识路由、Decision Context 依赖、判断方法、结果要求、能力依赖与验证限制，保证 Worker 能按需使用；通用领域适用性仍需案例和专业验证，不能以文件齐全或作者自检代替。
* **Worker 的任务执行约定**：Worker Skill 指导 Pi Durable Agent 理解本次 `task` 和 `instruction`，读取固定版 Root OM、按需加载相关知识，取得判断所需信息，并在当前用户身份及工具合同内推进工作。
* **Worker 的人工协作约定**：需要人介入时形成具体 DecisionRequest，并组织可理解的 Decision Context/Decision Brief。收到 UserDecision 后将其作为已回答问题的新输入继续处理；不足以推进时另行提问，不撤销已回答事实。Steering Input 作为一般消息理解，不自动转为 UserDecision。
* **Worker 的文件与工具约定**：使用本 Execution 的 Workspace 读取实际上传文件，通过运行环境提供的 MCP 能力访问业务系统；保留实际使用来源和必要限制，不把摘要当原文，也不凭调用发起推断业务效果。
* **Worker 的持续执行约定**：使用环境交付的 Session 历史与输入继续原工作。等待、消息续行、取消和未知工具结果的处理必须与平台控制规则及工具合同一致，不由 Skill 文本自行保证幂等、进程停止或恢复。
* **Skill 与环境配套交付**：设计 Worker Skill 时同时明确其依赖的工具、文件与 OM 读取方式、消息与执行控制能力，以及记录可用性。依赖能力缺失时明确阻碍，不宣称靠提示词即可工作；具体机制在技术设计与运行环境实现中落实。
* **装配与版本可查**：能够确认实际执行已装配 Worker Skill 和 Root OM，并从 Execution 定位实际 Skill/OM/Runtime 版本。改进 Skill 或环境时验证代表性执行、回答、消息续行及异常场景，不静默改变既有执行版本。

本章不规定数据库表、完整状态枚举或 Runtime 内部对象。后续设计仍需落实消息协调及交付恢复、取消收尾、token 后台使用与续期、Project 名称更新、历史保留与清理、文件限额及正式 API/MCP 合同；这些设计不得改变 Ontology 已确定的归属、关系和回答语义。CertLab 的资料检索、TestTask/Finding 交接和 Assessment 更新属于业务 MCP 与 OM 的应用场景，见 Narrative，不作为平台专属功能。

## User Experience

本章围绕核心使用场景梳理用户完成工作的路径，重点检查入口是否容易找到、信息是否足以行动、操作后是否有明确反馈，以及遇到阻碍后能否继续。功能规则以 Functional Requirements 为准，以下是体验设计要求，不代表已通过真实用户验证。

### 1. 从业务系统委托工作，再回来了解情况

用户在业务系统中发起某项工作，希望交给 Agent 后可以离开，之后再回来确认进展。

* 从业务系统直接进入对应 Execution，保留原业务工作的关联和返回入口；首次进入沿用现有用户身份，不要求另行注册、接受邀请或重新填写业务上下文。
* 创建请求已接受但尚未实际启动时明确说明，不让用户把“已提交”误认为“正在执行”，也不因等待而诱导用户重复创建。
* 执行详情优先回答“这次负责什么、已经做了什么、卡在哪里、是否需要我处理”。详细 Session、方法版本及工具记录按需展开，不要求用户先读完整历史。
* 用户离开页面后工作继续；再次从业务系统或 Project 进入时，能够快速定位原执行及其更新，不必重新描述任务。
* 没有待回答 DecisionRequest 时明确显示当前无需介入；Execution 结束时说明本轮已做工作、未完成事项及可查看的业务记录，不把业务正式完成混在其中。

**体验检查**：用户离开再回来，能否不阅读完整 Session 就判断是否需要行动，以及下一步去哪里。

### 2. 收到 DecisionRequest，理解问题并回答

用户需要处理某个 DecisionRequest，希望在足够理解问题后完成回答，而非先整理一遍 Agent 的执行过程。

* 从站内提示、业务深链或待回答列表直接进入目标 DecisionRequest，清楚标识所属 Execution 及工作范围，不要求从项目逐级寻找。
* Decision Brief 先呈现“需要我回答什么、为什么需要我、选项有什么影响”，再按需展开 Decision Context 的来源、版本、缺失和限制。查看原文后能方便返回原问题，保留已填写内容。
* 选项卡、文本框和文件上传围绕同一个问题组织。用户既能选择，也能补充观察、条件或其他意见；推荐项与用户实际选择清楚区分。
* 提交前能核对选择、文字及文件。离开或刷新存在草稿丢失风险时给予提示；上传失败不清空文字，也不把失败附件悄悄丢弃后当作完整提交。
* UserDecision 保存成功后立即显示“已回答”，让用户知道本次回应义务已完成，可以离开。消息交付和 Agent 继续执行的情况另行展示，不让用户为了等待后台结果而重复回答。
* 后续需要补充或更正时，能够找到已提交内容及更正入口。若 Agent 再次提问，应能理解新问题与原回答的关系，而非看到原问题无故回到待回答。

**体验检查**：用户能否完成“进入问题—查看依据—回答—确认已回答—离开”，中途查看资料或遇到上传失败也不丢失工作。

### 3. 补充消息和文件，让原工作继续

用户取得新材料、需要调整指示或想询问情况，希望直接告诉正在执行或已经结束的 Agent。

* 在 Execution 内容易找到 Steering Input 入口，输入文字、上传文件或提供引用即可，不要求先找到一个 DecisionRequest，也不要求先到业务系统登记文件。
* “回答此问题”和“向 Agent 发消息”在入口和反馈上区分清楚，避免用户以为一般消息已经代替某个 UserDecision。
* 提交后能看到消息已保存、文件是否已交付以及 Agent 的回应；后台暂未处理时保留消息，不以空白或持续等待让用户猜测是否需要重发。
* Execution 已结束时仍能使用同一消息入口，明确显示正在继续原执行；保留此前对话、文件和方法版本，不要求用户另建执行或再次上传同一输入。
* 查看其他执行时，当前输入属于哪个 Execution 始终清楚，避免文件或指示交给错误工作。

**体验检查**：用户能否用一次连贯操作补充材料并继续原工作，无需拆成多项判断请求或重复建立上下文。

### 4. 检查成果、停止工作或追溯过程

用户需要判断工作是否符合预期，必要时停止后续动作，或解释某个操作为何发生。

* 日常查看以进展、执行说明和业务记录链接为主；需要解释某个人工判断过程时进入对应 Decision Episode，需要查看完整经过时进入 Session。
* 检查 Agent 对系统做了哪些操作时，直接进入“MCP 操作”视图，先浏览全部调用，再筛选写操作，展开参数与返回，并打开可取得的业务记录链接核对，无需在完整对话中逐条查找 tool call。
* 写操作筛选下仍清楚提示是否有类型未知的调用；用户能够查看失败、结果未知和重试记录，不误以为列表只包含已完成的业务变更。返回执行概况或原列表时保留筛选和展开位置。
* 从 Decision Episode 能定位当时的 Decision Context、UserDecision 及相关 Session 消息；查看后可以返回原执行或原列表，保留筛选和浏览位置。
* 业务动作、文件处理或记录不完整时，清楚区分“已经确认”“尚未确认”和“无法读取”，不把未知状态包装为成果。
* 请求取消后立即反馈请求已接收，并继续呈现实际停止情况和已经发生的动作；用户不必反复点击才能确认系统是否收到。
* 结束、取消或发生异常后，用户仍能找到原执行、查看历史和了解未完成部分；继续工作的入口遵循同一 Execution 的消息规则。

**体验检查**：用户能否完成“查看概况—筛选写操作—展开参数与返回—打开业务记录核对”，再按需追溯 Decision Episode 或 Session；能否识别失败、未知及重试，并清楚知道停止请求和实际停止的区别。

### 5. 查看方法与在外部改进

用户需要理解执行依据；专家需要在外部工具中分析实践并维护 OM。

* OM 导航直接进入唯一仓库的文件浏览和搜索，不增加仓库选择步骤。搜索、阅读和历史查看始终显示所浏览版本。
* 从 Execution 查看方法时定位该执行固定的 OM 版本；切换浏览版本只是查看，不能让用户误以为正在执行的方法也已切换。
* 专家在熟悉的外部 Agent 中使用 OME Skill 设计与改进方法，沿用 GitHub/GitLab 进行方法维护；需要分析实践时，接入说明清楚提供 Airic Work MCP 的 token 配置方式和只读边界，不要求先进入平台学习工作流。
* 外部读取与工作台的记录缺失或不可读提示一致，用户能够理解为什么某段内容无法取得，不误以为取得了完整材料。

**体验检查**：用户能否找到准确版本，专家能否沿熟悉的工具链取得允许读取的记录，而不需要额外的平台审批或方法管理流程。

### 6. 首次配置与阻碍恢复

管理员需要让系统可用；普通用户遇到阻碍时需要知道下一步由谁处理。

* 首次配置将集成方认证、OM 来源和业务 MCP 连接的就绪情况集中说明，区分测试、保存和实际生效。配置失败保留输入，提示具体受影响能力。
* OM 未配置、身份失效、文件交付失败和运行异常分别说明原因及可采取的动作。能由用户完成的提供恢复入口，需要管理员处理的明确指向对应配置，不只显示错误代码。
* 用户管理能够区分自动接入后的使用资格和管理员权限；设置变更或停用被阻止时说明原因和仍需处理的事项，不让管理员靠反复尝试猜测规则。
* 无执行、无待回答事项、无搜索结果和无权访问分别呈现：说明正常空状态或具体限制，提供返回已可访问工作的路径，不把所有情况显示为系统故障。
* 网络中断、提交结果未知或后台失败时保留草稿和已提交内容，先帮助确认原操作情况，再提供相应重试；不要求用户从头重做整个场景。

**体验检查**：每个阻碍都能回答“发生了什么、我的输入还在不在、是否需要我处理、怎样回到原工作”。

## Narrative

以下为虚构场景，不是用户研究或真实业务规则。

一位材料评估人员在业务系统的大任务中发起附件检查。业务系统将授权目标和稳定任务引用交给 Airic Work；平台把相关执行组织在同一个 Project 下，依据实例唯一 OM 来源的最新确认提交启动，并记录 SHA。评估人员不必保持聊天窗口在线，后台 Agent 按 Worker Skill 加载固定版 OM，并使用该用户业务身份读取材料。

检查中发现补充说明缺少签署页。Agent 不把缺失材料自行解释为可接受，而是形成 DecisionRequest：列出正文版本、缺失信息、适用规则、建议及不确定性，说明正式效力判断受阻、独立附件核对仍可继续。评估人员从业务系统进入工作台，核对 Decision Context 原文及版本后给出限定判断。平台先确认正式处理记录，再显示实际继续事件；执行结束不被当作业务审批完成。

另一项判断中，工程师逐项选择“创建现场查验 TestTask”并补充检查范围，Agent 据此在 CertLab 创建事项。其他能够直接确定的测试和整改要求也由 Agent 形成业务产出，工程师通过 CertLab 汇总测试计划和反馈列表集中交接。结果返回后，工程师用 Steering Input 提交测试报告及客户回复；Agent 读取并核对固定资料和实际覆盖范围，通过业务工具登记交付/响应并更新相关 Assessment 草稿，未覆盖部分继续等待，需要新判断的事项再单独提交 DecisionRequest。通过 Steering Input 上传结果不代替 UserDecision，也不代表 Assessment 已正式确认；通过 UserDecision 提交则将对应 DecisionRequest 标记为已回答。

之后，专家在外部 Agent 中配置身份认证 token，通过 Airic Work MCP 读取本人可访问的 Session 和 Decision Episode。专家在外部环境使用 OME Skill 分析发现方法的适用边界需要澄清，结合对照案例验证后提交 GitLab Review。Airic Work 不运行反思任务或审阅学习发现，只在变更合并后同步文件与历史。后续执行使用新确认提交，原执行仍保留当时的 OM 和 Decision Context，便于解释过去发生的判断。


## 产品价值验证

选择少量具有代表性的真实业务工作，使用 Airic Work 完成委托、后台执行、必要人工回应、成果核查及补充继续的完整过程，观察：

* **是否减少总投入**：与原有方式相比，重复劳动和持续监督是否减少，节省的时间是否被准备资料、处理请求、纠正错误或维护系统所抵消。
* **成果是否可用**：按原有业务验收要求检查成果，是否存在重要遗漏，以及需要多少人工修正。
* **工作能否顺畅完成**：用户是否能够理解问题、提交回答、补充文件、核查操作并继续工作，是否出现需要开发人员介入才能推进的卡点。
* **接入是否足够通用**：接入另一类业务工作时，能否主要通过认证配置、MCP 能力和 OM 完成，而无需修改平台核心代码。

验证中区分领域方法不足、Worker 执行约定或装配问题、运行环境能力缺口和工具失败，不把所有偏差都归因于 OM。

初期通过实际使用、Session 记录和简短复盘验证，不要求专门建设指标看板或埋点系统。OM 改进时，用原案例及其他代表案例复查效果，避免只修好单个案例。

## 核心验收

| 场景 | 通过条件 |
| --- | --- |
| 单 OM 与全文搜索 | 导航直接到 /om，无列表/选择器；路径/正文可检索，范围固定当前 SHA，无向量依赖 |
| 新旧执行版本 | 新执行确认最新来源 SHA，失败不偷用旧缓存；同步不改旧执行来源和 SHA，继续原执行仍沿用 |
| 项目组织 | 相同业务系统实例及 `project_id` 归入同一 Project；名称不参与识别，不自动宣称业务完成 |
| 通用分工 | 同一业务任务可创建多个 Execution，以 `instruction` 描述各自分工，无平台子任务调度或自动合并 |
| 创建幂等 | 同键同内容返回原 Execution，同键异内容报冲突；同一 `task.id` 使用新键可创建另一 Execution |
| 自动创建用户 | 首次有效集成方 token 请求获取用户信息并创建本地 User，默认获得使用资格，发起用户即归属人 |
| 用户管理 | Airic Work 管理用户使用资格和管理员权限；停用不删除历史，重新认证不绕过停用，保护最后有效管理员 |
| DecisionRequest | 始终需要归属人回应；展示 Decision Brief、选项卡、文本框及可选上传，无跨 DecisionRequest 批量批准 |
| UserDecision | 提交成功即已回答；消息交付或业务操作失败不撤销回答，重试不重复保存或交付；更正保留历史 |
| Decision Episode | 与 DecisionRequest 一一对应，覆盖其生命周期并关联 Decision Context、UserDecision 和 Session 消息，不独立提取判断片段 |
| Steering Input | 可发送任意工作消息及文件，不要求关联 DecisionRequest，也不自动转换为 UserDecision |
| 结束后继续 | 收到新消息可继续原 Execution，沿用同一 Session、Workspace 和固定 OM SHA |
| Session | Trajectory 与 Session 为同一对象，消息及工具调用/返回可定位分页，不另建轨迹或审计实体 |
| MCP 操作查看 | 列出执行中的全部 MCP 调用，可按读取/写入/类型未知筛选；可展开参数和返回、打开可取得的业务链接并定位 Session；不额外创建操作实体 |
| 操作分类与结果 | 分类来自工具声明或连接配置，未知不归为读取且筛选时提示；请求正常返回不冒充业务成功；失败、结果未知和每次重试分别可见，凭据不进入记录 |
| 操作与判断关联 | 有明确记录关联时可在 Decision Episode 与相关调用间定位；无关联时不推测对应判断，返回后保留浏览位置 |
| Workspace | 每个 Execution 独立拥有；UserDecision 与 Steering Input 文件可交付读取，失败明确可见，等待及恢复时文件仍可用 |
| 业务能力边界 | 业务动作与文件处理遵循 MCP 合同，结果记录在 Session 中，不创建平台业务资料或执行结果实体 |
| OM 交付边界 | 固定 SHA 的 Root 常驻、其他知识按需加载；`.ome/` 不提交 Git、不由平台同步或加载，运行时不依赖本地作者文件 |
| 本人身份与外部读取 | 后台业务操作使用归属人身份；外部只读 MCP 使用 token 按同一用户规则读取，无独立委托或外部授权流程，无共享身份回退 |
| OME Skill | 沿用现有初稿，在外部开展方法设计及验证；Git 交付的 OM 有 Root、知识路由和能力依赖，不依赖本地作者材料 |
| Worker Skill 装配 | 实际执行可确认 Worker Skill 与固定 Root OM 已装配，Execution 可定位对应 OM/Skill/Runtime 版本；不以文件存在冒充已加载 |
| Worker Skill 与环境配套 | 在真实受控环境中走通读取 OM/文件、业务 MCP、DecisionRequest→UserDecision、Steering Input、结束后续行和取消/未知结果场景；Skill 文本或模拟运行不能替代能力验证 |
| 学习外置 | OM 维护仅需 Git 权限，分析 Session 时使用 Airic Work MCP；无内部学习中心，Decision Episode 不自动成为 Precedent |
| 可追溯性 | Execution→Session、DecisionRequest→Decision Episode→Decision Context/UserDecision 可定位，缺失和脱敏限制明确 |
