# Airic Work 产品定义与需求（更新版 PRD）

## tl;dr

Airic Work 是以 Operating Model（OM）驱动后台自主执行、以 Decision Request 组织人机协作的平台。业务系统通过标准 API 发起执行，唯一任务归属人依据 Decision Context 处理必要判断；平台管理 Trajectory 与 Decision Episode，并通过只读 MCP 向获授权的外部 Agent 提供实践记录。

每个实例只使用一个 OM 仓库，平台仅提供文件浏览、全文检索与 Git 历史；OM 构造、Reflection、验证和修改均在外部完成，通过 GitHub/GitLab Review 与合并采纳。新执行使用配置来源分支最新确认提交，实际启动后固定 Commit SHA。

状态：目标产品定义，不代表功能均已实现或验证。本版依据本次上传的 prd.md 及本线程已确认决定编写；上传原文件未被原地修改。产品名称 Airic Work，项目与仓库名 airic-work；本 PRD 与交互原型方案分开维护，原型不等同于实现契约。

## Goals

### Business Goals

| 目标 | 观察指标 | 目标值 |
| --- | --- | --- |
| 降低专业工作的人类实时监督成本 | 可比工作中的监督时长、介入次数及原因 | TBD |
| 保持或改善业务成果质量 | 权威业务验收结果、返工及人工纠正情况 | TBD |
| 提升后台可靠性与可追溯性 | 授权范围内执行成功、恢复与结果可核验情况 | TBD |
| 保持业务系统和工作台一致 | 同一执行/决定结果一致性、重复请求造成的重复效果 | TBD |
| 支持外部方法改进 | 授权轨迹可取得程度、版本关联完整性及改进后的代表案例表现 | TBD |

不以运行量、聊天量、PR 数量或不完整记录中的出现频率替代实际价值。

### User Goals

* 业务系统能够可靠发起、查询和取消授权范围内的 Agent 执行，无需重建运行时。
* 任务归属人无需持续打开聊天窗口，在需要时集中理解判断问题、信息依赖及影响。
* 用户清楚区分 Agent 结束、决定已记录、工作实际继续与业务正式完成。
* 专家和外部 Agent 能取得获授权的实践记录，在熟悉的环境中改进 OM。
* 管理员集中维护用户和连接，用户自己确认业务身份并管理本人授权。

### Non-Goals

* 不自建 Git 服务、分支/PR/MR/Review/审批/合并或 OM 发布晋级流程。
* 不建设平台内学习中心、反思任务、学习发现审阅、改进候选管理或自动修改 OM。
* 不提供多 OM 仓库列表、执行时 OM 选择器、Decision 语义对象管理、关系图、Knowledge Gap 看板、embedding 或向量检索。
* 不取代业务系统的数据、权限、审批、事务和专业 UI；不为每个业务 App 开发深度定制 Agent 集成。
* 不取代 Codex、Claude Code 等通用交互式 Agent，不重建完整 Harness，不强制上传完整外部会话。
* 不支持成员邀请、自助注册、多人抢占/竞争处理 Request，也不宣称完整实现 Attention Cycle。

## User Stories

### 任务归属人

* 作为任务归属人，我希望按 Project 查看相关 Execution，以便理解同一业务大任务的工作情况。
* 作为任务归属人，我希望看到判断需要的信息、来源版本、缺失项与影响，以便不通读完整轨迹也能负责地作出决定。
* 作为任务归属人，我希望正式决定与聊天询问分开，以便处理结果具有明确依据与审计记录。
* 作为任务归属人，我希望 Agent 使用我本人的业务身份，并在授权失效时明确说明受影响操作，以便避免越权与错误恢复。

### 业务系统集成方

* 作为集成方，我希望通过统一 API 创建、查询、取消执行并处理 Request，以便在业务界面与工作台获得一致结果。
* 作为集成方，我希望重试不重复启动执行，取消结果和已产生效果可查询，以便处理网络异常而不造成重复业务动作。

### 专家与外部 Agent 使用者

* 作为专家，我希望按权限读取 Trajectory 与 Episode，以便在外部重建实际情境、分析偏差并验证方法修订。
* 作为 OM 维护者，我希望沿用 GitHub/GitLab 的文件和变更审核流程，以便不维护另一套知识治理系统。
* 作为 OM 阅读者，我希望全文搜索文件名、路径和正文，并明确当前 SHA，以便找到准确版本的指导。

### 管理员

* 作为管理员，我希望直接创建、编辑和启停用户，以便集中管理而不依赖邀请流程。
* 作为管理员，我希望分别维护唯一 OM 来源、业务连接及外部只读 MCP 策略，以便技术配置不被误认为用户业务授权。

## Functional Requirements

以下优先级为本版建议实施分级，不代表已排期或已交付。P0 为核心闭环，P1 为应补齐的管理体验。数据库对象、完整状态机及 API 字段尚未定稿。

### 工作组织与标准执行服务（Priority: P0）

* 业务任务由业务系统拥有，说明业务目标、义务及正式完成条件；Agent Execution 由 Airic Work 管理，记录授权目标、范围、进度、结果和实际执行版本。
* Project 将多个 Execution 关联到业务系统的一个大任务对象，使用稳定业务引用；不拥有权威业务完成状态，不承担自动调度、结果合并或自动完成。
* 本轮以一个 Execution 归属一个 Project 为设计基线；跨 Project 共享/迁移、Project 负责人继承及业务义务覆盖方式待设计。
* 每个执行任务只有一位归属人；其 Request 由该归属人在相应权限内处理。不增加抢占、竞争处理或独立分派机制。
* 业务系统通过标准任务 API 创建、查询和请求取消执行；工作台共用相同应用服务与记录，不维护第二份状态。
* 创建支持幂等。请求被接受不等于已启动；取消被接受不等于实际停止。取消只停止后续工作，不回滚已经发生的业务效果。
* 等待人工判断时，在依赖与权限允许的情况下继续无关工作。局部等待、恢复、取消收尾和完整生命周期仍需详细设计。
* 后台不依赖前台会话持续存在。Pi Durable 为目标运行时，其内部对象不直接等同于产品对象。

### Decision Context 与人工决定（Priority: P0）

Decision Context 是人或 Agent 作出判断需要的信息及其依赖，包括业务事实与状态、规则/文档、既往决定、授权要求、来源版本、缺失项与不确定性。证据只是其一部分，不将所有上下文都缩减为证据附件。

* 显示需要什么信息、从何取得、是否可用且当前有效、缺失影响什么判断，以及哪些工作可以继续。
* 缺当前事实、专业方法不足、工具能力缺失和授权不足分别表达，不把所有 Request 当作 OM 缺陷。
* Decision Model 是 OM 文件内的可复用 Judgment Knowledge，不是平台独立治理的对象。Request 可引用文件路径、位置与 SHA，不要求语义索引或独立模型 ID。
* Decision Brief 面向人组织当前问题、触发、已知事实、假设、Context 依赖、方案/建议及理由、风险、不确定性、影响与所需动作。
* Context 引用尽可能包含来源系统、稳定对象 ID、版本、位置与必要 Revision；摘要不能替代原始权威资料。读取原文另受来源权限限制。
* Request 支持适用的专业判断、补充事实、限定授权或进一步调查；动作范围按该请求和本人权限决定。
* 正式 Resolution 必须关联具体 Request、处理人、依据与版本；普通聊天消息不自动成为决定。进一步调查不自动解决原问题。
* 提交时校验 Request、Context、业务状态和权限仍有效。单一归属人并不取消重复提交、跨界面重试与版本变化校验；重复或过期处理不静默覆盖。
* 处理结果接受与实际执行继续分别记录。Request 中的同意不能替代业务正式审批，也不自动创建身份委托。

### 单实例 OM 文件管理（Priority: P0）

* 每个实例仅配置并使用一个 OM 仓库与来源分支；所有 Project/Execution 共用该来源，不按项目选 OM，不提供仓库列表或执行时选择器。
* 平台将 OM 视为 Git 文件，展示目录、Markdown/文本正文、Git 提交历史、提交描述、变更文件与 diff，并提供 GitHub/GitLab 外链。
* 文件可包含 Decision、关系、Knowledge Gap、Precedent 和验证材料，但不提取成平台语义对象、知识图谱或管理工作流。
* 提供关键词全文检索，覆盖文件名、路径与正文。结果显示路径、命中片段与高亮，点击打开文档并定位命中；支持清空、无结果和读取失败状态。
* 搜索严格限定当前选定的已同步提交快照，默认当前同步版本；显示分支和 SHA，不跨版本混合。不引入 embedding、Chroma 或其他向量库。
* 新执行实际启动前确认配置来源分支最新提交，解析并记录实际仓库来源和 Commit SHA 后运行。不能将旧缓存冒称最新；无法确认时不允许静默按旧版启动。
* 执行启动后固定该 SHA；同步新提交和切换浏览快照不改变进行中或历史执行依据。历史读取应保留原来源与版本关系。
* 未配置时显示单仓库空状态，管理员前往 Git 设置，成员联系管理员；不提供新建 OM 产品流程。
* 仓库来源变更不能重写历史。变更影响、历史保留及恢复机制需专门设计，不预设无缝切换。

### Trajectory 与 Decision Episode（Priority: P0）

* Airic Work 持久化自身后台执行的行动、观察、工具结果、正式决定、人工干预与后续结果，以及恢复/审计所需关联。
* 记录实际 OM、Runtime、Skill 版本、业务主体、技术执行者和必要 Context 来源版本；调用发起与权威结果确认分开。
* Trajectory 支持按执行、事件类型、时间及 Request 定位和分页。记录缺失、压缩、清理、脱敏或不可访问时明确覆盖限制；不展示隐藏思考链。
* Episode 围绕一次实际判断关联情境、Context、所用知识修订、结论、干预和结果，并链接原始轨迹。
* Episode 是实践片段，不自动成为正确知识或正式 Precedent。
* 外部会话原始记录属于用户所选环境，不强制上传完整会话。本版不承诺任意外部轨迹导入或学习成果回传服务。

### 外部只读轨迹 MCP（Priority: P0）

* 对外提供获授权执行记录的定位、Trajectory 分页读取、Episode 读取及理解记录所需的版本/Context 引用。
* 不允许通过该 MCP 创建/取消执行、提交 Resolution、修改 OM、重放业务动作或读取令牌。
* 每次读取校验用户/客户端身份、资源范围、当前授权及来源数据外发策略；不能继承原 Agent 的业务权限，也不能凭记录 ID 或引用获得内容。
* 仅交付获授权且必要的脱敏记录；缺失/脱敏限制与工作台一致，引用不等于业务原文访问权。
* 保存调用用户/客户端、范围、时间与允许/拒绝结果的读取审计，日志不存秘密。
* 授权撤销阻止后续读取，不声称追回已经合法交付的内容。工具名、认证、传输、分页一致性及客户端授权协议待设计。

### 本人业务身份与授权（Priority: P0）

* 平台用户与业务系统实例中的稳定 externalSubjectId 建立可验证关联，不按同名或相同邮箱自动绑定。
* 身份映射、本人委托和具体业务对象/动作权限分别校验；映射存在不等于已授权，授权有效不等于目标动作有权。
* 业务 MCP 读写均代表执行归属人本人，不回退到管理员、共享服务账号或其他用户。技术客户端身份不能替代被代表的业务用户。
* 区分技术调用方、实际发起人、执行归属人/业务主体、Agent 技术执行者和实际决策处理人；调用方不得任意填 userId 冒用他人。
* 管理员维护验证映射，不能代用户同意委托、读取令牌或以管理员身份测试成员业务权限。
* 每次业务调用和执行恢复重新校验当前委托、主体、范围与业务权限；浏览器登录会话与后台授权生命周期分开。
* 过期/撤销/外部主体停用/权限收窄阻止受影响操作；允许无依赖工作继续，不回滚已有业务事实。
* 本人重新授权后确认仍为同一主体、合法范围和当前业务状态再恢复；未知业务写入先核验回执，不盲重放。
* 本轮身份关联基线为每用户每业务实例一个有效主体，同一外部主体不映射多个平台用户；可关联多个业务系统。生产协议与受限续期机制待验证。

### 管理与个人设置（Priority: P1；权限保护为 P0）

* 单组织，管理员/成员两类平台角色；管理员直接创建、编辑、启用和停用用户，无邀请、接受步骤、自助注册或默认密码。生产登录初始化、SSO 和重置机制待设计。
* 用户列表支持名称/登录标识搜索及角色、状态筛选；账户有效性与业务身份就绪程度分开。
* 校验唯一登录标识；禁止停用自身、停用或降级最后有效管理员。有未交接执行/待决责任时阻止停用，不因此新增转派流程。
* 停用保留历史，恢复账户不自动恢复外部授权。身份映射变更不能使运行中执行静默换人，历史主体不改写。
* 系统设置包括组织/时区、唯一 Git 来源、业务系统实例与 MCP 连接、标准 API 说明、外部只读 MCP 策略、Runtime 能力/版本、记录保留摘要与审计。
* 技术连通测试、配置保存和实际生效分开；技术连接成功不表示本人业务授权有效。未知依赖影响时阻止破坏性变更。
* 个人设置支持显示名、语言/时区、待决/异常/结果更新站内提示，以及本人业务账号验证/授权状态、范围、重新授权、只读测试和撤销。
* 外部读取客户端授权与出站业务委托分别展示与撤销；通知已读不等于已处理 Request。

### OME 与 Skill 方法体系（方法边界：P0）

OME Skill 和 Airic Work Skill 为两个顶层方法入口，Reflective Learning 是 OME 内部按需加载、可单独调用的模块。两者不是上下级 Agent 的持续委派机制，也不要求共享会话或执行生命周期。

| 方法 | 职责 | 使用边界 |
| --- | --- | --- |
| OME Skill | 从案例构造、评审、验证和持续修订工作方法 | 专家与外部 Agent 环境，成果通过 Git 管理 |
| Reflective Learning 模块 | Observe、Reflect、Attribute、Propose、Synchronize、Revisit，区分事实、解释与候选 | 外部环境读取获授权轨迹后开展；不由 Airic Work 后台调度 |
| Airic Work Skill | 理解目标、读取固定版 OM、路由判断、取得 Context、受控操作、提出 Request 与使用有效结果 | Airic Work 后台；具备相应工具与权限的外部环境也可使用 |

Decision-centric OM 与评价分解

OM 的重点是可复用的专业 Judgment。确定性步骤优先交给业务系统或确定性程序。Decision Discovery 优先从 Evaluation Decomposition 出发：什么算 good enough、何时拒绝、如何比较候选、何时停止改进。

Good Enough 表达目标、风险与成本下可接受的结果范围和停止条件。Verifier 是理解与检验判断的视角，可覆盖选择、权衡、诊断、优先级、不确定性和升级，不要求二元结果。Agent 可以在判据和权限内探索 Discretionary How；有依据的法务、合规、业务或安全 Mandatory How 必须保留适用条件与履行证据。

这些语义由既有 Judgment、Objective、Constraints、Outcomes、Validation 等内容承载，不新增强制 Schema。Decision 可以包含 Question、Trigger/Applicability、Context Dependencies、Judgment、Outcomes、Precedents、Knowledge Gaps、Validation 及可选 Authority/Feedback。Root OM 定义范围、路由知识和领域能力依赖；Decision 的适用条件不替代业务系统发起执行时的明确目标和范围。ADR 可以是 Precedent，也可能仍是当前有效约束。

OME 构造、验证与改进

* 从代表案例、专家经验与可核验知识重建工作；区分成果样例、真实过程记录、专家解释、模型候选知识和业务能力合同，不能把模型推测写成已发生实践。
* 定义有效产物与完成条件，分解评价，识别工作边界，利用正反例、边界例和最小变化对照提炼 Judgment、例外、停止条件及必要过程。
* 设计缺事实、缺判断、缺工具时的承接与恢复路径，映射实际 Runtime/MCP 能力；能力缺口不能靠增加规则文本掩盖。
* 验证前说明判据来源、允许结果范围与不确定性处理。区分静态检查、情景推演、模拟工具与真实受控运行。
* 原案例用于解释核对；未参与提取的案例、独立复核或可核验结果用于检验迁移。同一 Agent 自拟方法、案例、预期后自评通过不是独立确认；独立 Agent 仍可能共享错误假设，不等于领域权威或真实业务结果。
* 分析偏差时比较规则缺失、未加载、知识不足、Context 路由、执行偏差和工具缺陷等替代解释；证据不足可提出待验证假设或决定暂不修改 OM。
* 外部学习可形成 Knowledge Delta、Reflection Finding 和 Improvement Proposal，但这些不是平台存储、审阅或流程对象。
* 方法修订经外部专业澄清、必要验证与 Git Review 后采纳，观察后续收益与退化；单次失败或成功都不足以证明因果。

## User Experience

### Entry Point & First-Time Experience

主要入口是业务系统的执行/Request 深链，也可从工作台项目列表进入。管理员先配置唯一 OM 来源与业务连接，集中创建用户；用户确认本人业务身份并完成必要授权。没有邀请流程或通用手工新建执行入口。

OM 未配置时显示空状态：管理员进入 Git 设置，成员联系管理员。无待决时显示无需处理并允许查看进展。平台角色不自动赋予业务数据访问权。

### Core Experience

1. 在 /projects 查看可见项目，进入 /projects/:projectId 的执行/待决 Tabs；只聚合有权查看的数量。
2. 在 /executions/:id 查看目标、唯一归属人、业务主体、授权状态与实际 OM SHA。左侧进展/结果/轨迹，右侧 Request 与 Brief；窄屏切为 Tabs。
3. 阅读 Context 依赖并打开来源 Drawer，查看版本、原文、缺失影响与可继续工作。选择请求允许的处理方式，核对理由和范围后正式提交。
4. 先显示处理已记录，再依据实际事件显示继续；Agent 结束仍与业务系统完成状态分开。询问执行情况不自动生成 Resolution。
5. 从执行进入 /executions/:id/trajectory，再进入 /episodes/:episodeId 查看具体判断片段。外部 Agent 通过独立授权只读 MCP 取得允许记录，在外部分析并提交 Git 变更。
6. 导航“OM”直接进入 /om 文件浏览、全文搜索与正文，无列表页。历史为 /om/history，提交为 /om/commits/:sha；文档深链用 /om?commit=:sha&path=:filePath。
7. 同步 Git 后展示新提交内容；未来执行确认最新 SHA 后启动，旧执行仍保留原版本。浏览历史不能改变运行版本。

系统设置 /settings/system/:section，用户管理 /settings/users，个人设置 /settings/profile。所有路径均为 UI 路径，不代表已发布 API。

### Edge Cases

| 情况 | 必须行为 |
| --- | --- |
| Context 或业务版本已变化 | 保留草稿，说明变化并要求复核，不套用过期决定 |
| 重复提交或结果未知 | 查询同一操作/权威记录，不盲目重发或静默覆盖 |
| 取消延迟或写入效果未知 | 分别显示请求接受、实际停止与已有/未知效果 |
| 授权过期或对象无权限 | 阻止受影响动作，不换管理员或共享身份兜底 |
| Git 同步失败 | 历史可浏览，明确未确认最新，不静默用缓存启动新执行 |
| 轨迹缺失、脱敏或已清理 | 明确覆盖限制，不伪造完整记录或学习结论 |
| 外部读取越权 | 拒绝且审计，不泄漏不可见对象及计数 |
| 无最后有效管理员或有未交接责任 | 阻止账户破坏性操作，保留历史 |
| 未知页面/越权访问 | 提供404/不可用或403，不通过隐藏菜单替代校验 |

## Narrative

以下为虚构场景，不是用户研究或真实业务规则。

一位材料评估人员在业务系统的大任务中发起附件检查。业务系统将授权目标和稳定任务引用交给 Airic Work；平台把相关执行组织在同一个 Project 下，依据实例唯一 OM 来源的最新确认提交启动，并记录 SHA。评估人员不必保持聊天窗口在线，后台 Agent 使用其本人有效授权的业务身份读取材料。

检查中发现补充说明缺少签署页。Agent 不把缺失材料自行解释为可接受，而是形成 Decision Request：列出正文版本、缺失信息、适用规则、建议及不确定性，说明正式效力判断受阻、独立附件核对仍可继续。评估人员从业务系统进入工作台，核对 Decision Context 原文及版本后给出限定判断。平台先确认正式处理记录，再显示实际继续事件；执行结束不被当作业务审批完成。

之后，专家授权自己的外部 Agent 读取相关 Trajectory 和 Episode。外部 OME 分析发现方法的适用边界需要澄清，结合对照案例验证后提交 GitLab Review。Airic Work 不运行反思任务或审阅学习发现，只在变更合并后同步文件与历史。后续执行使用新确认提交，原执行仍保留当时的 OM 和 Context，便于解释过去发生的判断。

## Success Metrics

### User Metrics

* 可比工作的实时监督时长、介入次数、原因及 Context 重建/处理时间。
* 用户能否辨别所需信息、缺失影响、决定接受与工作继续的区别。
* 本人授权修复后能否按正确主体恢复，且不重复未知业务动作。

### Business Metrics

* 业务验收质量、返工及人工纠正情况。
* 同类工作注意力成本与可交付成果的变化。
* 外部 OM 改进后的代表性场景是否改善、相邻场景是否退化；这是跨系统评估，不要求平台学习看板。

### Technical Metrics

* 执行成功/失败/恢复与记录可追溯覆盖。
* API 幂等与跨界面一致性，取消及未知结果的可核验程度。
* Git 最新确认、历史 SHA 固定与全文搜索版本一致性。
* 外部读取授权、脱敏及审计覆盖；业务身份错误或越权防护。

统计单元、采集覆盖、基线与量化目标均为 TBD。不把采集缺失当作事件未发生，不用自评替代业务质量验证。

### Key Events to Track

建议跟踪创建请求接受/实际启动、取消请求/实际停止、Request 创建/打开/处理接受/后续继续、Context 失效、本人授权变化、业务调用结果确认/未知、Git 同步与实际 SHA 解析、全文检索与文档打开、轨迹分页读取及外部允许/拒绝、用户/映射配置变更。事件名与 Schema 待设计；分析记录不包含秘密或无必要业务正文。

### 职责与权威来源

| 对象 | 权威来源 | Airic Work 职责 |
| --- | --- | --- |
| OM 文件与修订 | Git 仓库及 GitHub/GitLab | 获取、文件展示、全文检索、历史/diff与执行版本关联 |
| 业务事实、状态、证据、任务完成与审批 | 业务应用 | 按本人业务权限访问和引用，核验权威回执 |

| 学习分析、候选修订与外部会话 | 外部 Agent/专家环境 | 仅提供经授权实践记录，不建设内部学习服务 |
| OM 变更审核与合并 | GitHub/GitLab | 外链及历史关联，不复制审批流程 |

### 运行约束

Pi Durable 目标标准能力包括文件、Shell/代码执行、文本/结构化数据处理、常见文档处理与 Context 检索；实际可用能力必须以发布说明和验证为准，不能从本地 Codex 能力推断后台能力。

OM 声明领域能力依赖，不绑定模型、Harness 工具名、MCP Endpoint 或凭据。Runtime 的文件、Shell、网络、敏感数据和工具访问需隔离边界；业务写入经业务受控接口完成，考虑幂等、权威回执、失败重试与恢复。

Skill 是行为方法，不是权限、事务或状态机。Runtime/模型/Skill 升级需代表性 OM 和回归案例验证，不静默改变已有执行版本。

### 已确定与待详细设计

已确定：单实例单 OM、Project 组织多个 Execution、单一归属人、Decision Context、本人业务身份、内外共用任务/决策服务、外部学习和对外只读轨迹 MCP。

仍待设计：执行粒度/完整生命周期、重试与业务覆盖、Project 迁移/负责人关系、取消收尾、聊天协调、来源分支默认与确认时限、Git 同步/切源与历史保留、MCP 契约/传输/分页/客户端授权、认证/身份可信关联/续期、留存/脱敏及指标口径。

现有代码、完成度和迁移另行审计。airic-work 为独立实现主线；旧 airic-forge 计划在保留必要工作和资产后归档，不表示已完成归档或仓库创建。旧 Work/Turn、深度 App 集成或自建治理不自动成为新契约；适用组件和历史资产按需要评估迁入。

## UI Architecture

* 前端目标：React + TypeScript，原型建议 Vite 与 React Router BrowserRouter；生产构建/部署方案另行确认。
* 组件：真实 @mui/material、@mui/icons-material、@emotion/react、@emotion/styled，采用 ThemeProvider、CssBaseline、MUI 默认排版/间距/交互规范。现有 Tailwind 原型不是已完成的 MUI 实现。
* 布局：浅色紧凑工作台，侧栏导航、AppBar、Paper、Table、Tabs、Drawer、Dialog、Alert。桌面执行/待决并置，窄屏 Tabs 与临时导航；表格局部横滚，不遮挡操作。
* 状态：服务端权威记录与本地草稿分开，草稿不等于 Resolution；生产状态管理库待选。原型可用统一模拟服务及虚构 localStorage 数据，不存令牌。
* 文件安全：安全 Markdown/文本渲染，禁不安全 HTML；相对链接限定同仓库同提交，校验路径和权限，二进制不伪造预览。
* 交互：加载保留布局，失败局部重试，保存/决定结果持久可见，提交防重复，脏值离开保护，返回恢复过滤/滚动。
* 可访问：键盘可达、可见焦点、模态焦点恢复、状态文字不只靠颜色、减少动态效果。MUI 默认组件不能替代完整可访问验证。

## API & Backend

### 服务结构

统一应用服务承接工作台和业务系统请求，后台 Runtime 负责内部调度、检查点和推进。公开 API 表达产品操作，不开放任意内部状态修改。

后端框架、数据库、ORM、认证提供方、队列与托管均 TBD，不将原型的无数据库实现当成生产架构。

### 标准 API 能力

| 能力 | 契约要求 |
| --- | --- |
| 创建执行 | 可信发起身份、唯一归属人、业务/Project关联、明确目标范围、幂等；OM取实例来源，不提供任意OM选择 |
| 查询执行 | 进展、结果、实际来源/SHA、已确认与未知效果、相关引用 |
| 请求取消 | 记录请求与实际结果，保留已发生业务效果 |
| 查询 Request | Brief、Decision Context、允许动作、处理记录及必要版本 |
| 提交处理结果 | 关联具体Request和本人，校验权限与当前版本，记录接受结果和后续 |

正式 URL、资源 Schema、错误结构、通知/Webhook 与认证方式 TBD；不把界面路由作为正式接口。

### 数据与安全

核心概念为实例配置、User、Project、Execution、Request/Resolution、Context 引用、Git 修订/文件快照、TrajectoryEvent/Episode、身份映射、委托、外部只读授权和审计。它们是设计概念，不要求一一建表。没有 Invitation、DecisionIndex、KnowledgeGap 管理、内部 Analysis/LearningFinding/Proposal 服务。

* 每次服务端操作校验当前会话/调用身份、对象权限及必要委托；不能仅隐藏按钮。
* 当前授权与不可改写的历史身份快照分开；重新映射/授权不改变旧审计。
* 凭据在服务端安全托管，仅传必要引用；不回显给浏览器、OM、提示词或轨迹。
* 外部 MCP 复用授权记录查询，不建立第二份轨迹；每页读取受当前范围与数据策略控制。
* 未知外部副作用先查询权威回执，同一操作身份不因重试随意更换。

## Performance & Scalability

具体规模、SLA、延迟、吞吐、并发、留存天数及成本目标 TBD，不作未经验证承诺。

* OM 文件与全文检索结果按仓库来源及 SHA 隔离快照；缓存标明同步时间，不能代表启动时最新确认。
* Trajectory、历史与审计使用分页/按需加载，较大文件/diff 限制体积并提供外链；检索及读取后台可扩展实现但不引入向量检索需求。
* 服务端统一权限检查，缓存不能跨用户或授权范围泄漏。授权撤销后的缓存与分页续读行为需验证。
* 前台关闭不应终止后台工作；恢复依赖持久记录、当前授权和副作用核验，不依赖聊天历史完整存在。
* 监测同步失败、授权拒绝、Runtime 异常、恢复失败、未知业务效果、重复操作和外部读取审计。日志脱敏且不采集隐藏思考链。
* 无障碍合规等级待确认；至少验证键盘、焦点、语义标签、错误提示和窄屏可用性，不把组件库使用等同于合规。

### 核心验收

| 场景 | 通过条件 |
| --- | --- |
| 单 OM 与全文搜索 | 导航直接到 /om，无列表/选择器；路径/正文命中可定位，范围固定当前SHA，无向量依赖 |
| 新旧执行版本 | 新执行确认最新来源SHA，失败不偷用旧缓存；同步不改旧执行来源和SHA |
| 项目组织 | 同一业务大任务可关联多个执行，不自动宣称业务完成 |
| 判断协作 | 信息依赖、缺失与可继续部分明确；聊天不生成正式决定，接受与继续分开 |
| 唯一归属人 | 无抢占/多人争用流程；重复请求与版本变化仍校验 |
| 本人身份 | 出站业务调用使用归属人本人有效委托，失效阻止受影响动作，无共享/管理员回退 |
| 外部读取 | 合法记录分页可读，越权/撤销拒绝并审计，不暴露秘密或额外业务原文 |
| 学习外置 | 无内部学习中心/反思任务/候选管理，外部修改经Git Review，Episode不自动成为Precedent |
| 账户管理 | 无邀请，重复标识拒绝，最后管理员和未交接责任保护有效 |
| 可追溯性 | Execution→Trajectory→Episode→Context/固定OM文件可定位，缺失和脱敏限制明确 |
