# Operating Model Engineering — OME v0.5.3

帮助 Agent 与领域专家构造可复用、可检验的判断知识。目标是 **Judgment Reuse**：让后续执行者知道在什么情境下，依据哪些事实、规则和经验评价结果、比较选择、处理不确定性，以及何时已经 good enough、需要继续改进或交给人判断。

## 方法假设与使用边界

本版采用一个待实践检验的假设：特定领域的知识、隐性规则和专家经验可能集中在关键判断点（Knowledge Hotspots）；围绕这些点组织知识，可能提高正确取用、专家协作和反馈复用的效率。

通用流程与工具使用的能力是设计起点，具体瓶颈仍需从任务证据判断。工具选择也可能承载专业判断；上下文获取、工作恢复和工具合同也可能成为主要问题。不要将所有失误解释为缺少 Decision，或将知识组织方式的收益与新增知识、模型和工具的收益混淆。

**从 Evaluation Decomposition 入手发现 Decision**：什么算可接受，什么情况应拒绝，怎样比较候选，何时应停止改进？Verifier 是理解和检验这些判断的视角，可以是判据、比较方法、诊断证据或专家复核；不预设所有 Judgment 都有二元答案或确定性校验器。

## 核心组织原则

1. **Decision 是判断知识的聚合中心。** 优先复用专业 Judgment、Acceptance / Evaluation Criteria、Context Dependencies、Precedents 和 Knowledge Gaps；沿用 Trigger / Applicability、Objective、Constraints、Judgment Basis / Method、Outcomes、Feedback 和 Validation 等现有结构承载。判断可涉及接受、选择、权衡、诊断、优先级、不确定性和升级，不要求 DDD aggregate，也不规定一个 Decision 对应一个任务或数据库对象。
2. **Root OM 是常驻的工作体系入口。** 说明应用对接、工作类型、知识架构、路由、加载与公共约束；可以没有直接关联的 Decision。创建或实质重构时先形成最小整体地图，再选择代表性工作类型深入。按需设置工作类型/Workflow 子 OM，描述必要工作依赖与协作恢复；一个环节可使用多个 Decision，同一 Decision 可跨环节复用。Decision-centric 规定判断知识的聚合方式，不要求知识树每层都有 Decision。
3. **Subject Knowledge 提供判断素材。** 标准、专业概念和共享知识可独立维护、按版本引用；Decision 说明这些知识如何影响选择。当前事项事实与原始输入由业务系统或宿主按职责留存，OM 用引用关联。
4. **上下文依赖需要说明判断作用。** 明确依赖影响什么区分、何时必需、充分性、权威和版本要求、获取路径，以及缺失、冲突和变化后的处理；不把资料清单当成完整契约。依赖可通过资料、人工观察或专业结论、已有业务记录取得；信息尚未数字化时，明确需要谁针对什么范围直接提供判断。
5. **为反馈设计方法。** 在设计 Decision 时发现谁能评价、通过什么信号、何时取得反馈；为人准备简洁 Decision Brief，保留实际判断、理由、证据和适用范围。当前事项的决定权与知识的可推广性分别判断。
6. **共享案例来源，Decision 拥有其案例解读。** 源事件/Decision Episode 保留实际情境、证据、判断、原有理由与结果；不同 Decision 可引用同一来源，分别说明判断用途、解释与迁移边界。已采用且用于运行时的简短解读可内联，较长内容放对应 Decision 的案例文件；确实跨 Decision 复用的解读可独立维护并注明引用目的。解读经反思、必要验证与现有采用机制成为 Precedent / Judgment Case，不把重建的解释写成当时理由，也不直接迁移历史结论。
7. **业务状态由确定性 Domain Model 维护。** Agent 经授权 API / MCP 操作；业务系统负责权限、状态、事务、版本冲突和回执。OM 组织判断知识，不能代替这些约束。
8. **给方法探索留出空间，保留必须遵守的过程。** Discretionary How 由 Agent 在目标、判据和权限内探索；Mandatory How 来自适用的法务、合规、业务、安全等要求，需保留来源、适用条件与履行证据。随着模型能力变化，可以调整建议做法；结果可接受不自动豁免强制过程。
9. **Good Enough 是有条件的接受与停止判断。** 结合用途、风险、成本和剩余不确定性说明可接受范围、必须补齐的缺陷，以及继续改进的预期价值。成本耗尽可能意味着有限交付、未决或升级，不能自动证明结果合格。

## 进入任务与按需加载

先读取目标、已有 OM、代表性案例、可取得的轨迹，以及相关业务合同。复用用户已经确定的选择，识别当前活动：

| 活动 | 方法与资料 | 适当产出 |
| --- | --- | --- |
| Create | 读 [整体地图、案例推导与 Decision 发现](references/derivation-method.md)、[知识对象契约](references/artifact-contracts.md) | 常驻入口、最小整体地图、候选方法及依据、Gap 和验证安排 |
| Review | 对照知识对象契约，检查工作类型、知识路由和案例解读的归属；按问题读其他方法 | 有证据的差距、优先级和具体改进方向；不默认改写 |
| Improve | 从已定位的 Decision / Gap 加载所需设计方法；需要实践归因时按需用 [Reflective Learning](references/evaluation-learning.md) | 有适用范围的最小候选修订、案例与验证证据 |

## 先澄清工作场景

开始构造 OM 或从执行偏差学习时，先用真实工作片段核对五项共同前提：业务为谁交付什么结果；Agent 承担什么角色与授权；哪些事由谁确认；什么是正式输入；发现问题后由谁处理、如何恢复。检查这些前提是否改变多个工作项的动作顺序、提问门槛或停止条件。

同一个前提影响多个判断时，将它写入适用的共享入口。跨工作类型的目的放 Root，系统权威放应用约定，特定工作类型的角色、授权、输入与闭环放工作类型 OM。条款 Decision 引用共享约定并承载局部专业判断。用另一工作项验证迁移及例外范围。

## 开展 OME

创建或实质重构 OM 时，先明确整体范围、应用边界、工作类型和知识入口，建立足以导航的 Root OM；规模需要时引用 architecture-map。Root 按常驻方法入口编写，由宿主以明确版本装配进 system prompt 或等效指令上下文，具体方法、Decision 和案例按需加载；作者约定不代表装配能力已经实现。

OM 的正式目录面向运行时判断；构造资料、访谈、原始案例底稿、候选解读、tests 与完整验证记录集中在作者工作区 `.ome/`。Root 常驻，其余知识按当前问题逐步加载，不因来源或关联链接扩读研究档案。采用后确需用于判断的 Precedent 只提炼最小解读、适用范围与必要证据；运行时保留来源/版本、方法限制与简要验证状态。

从地图中选择一个工作类型及有用途的代表案例，先分解评价：下游能否使用、何时拒绝、候选如何比较、何时停止。由这些问题发现判断热点，再回看过程中的关键区分、必要依赖与协作，建立最小工作闭环；案例发现持续修正地图。局部修订只检查受影响路由。

将候选 Decision 写成可辨识的问题，检验知识聚合粒度，再用正反例、边界例、对照案例和专家协作提取依据。先分析现有资料、提出候选解释，再问能区分判据、偏好与强制约束的问题。每轮回答修订相关方法或案例，标明已记录、专家陈述、模型推断和待验证内容。建议步骤只在确有帮助时保留，Mandatory How 则明确其来源与约束范围。

保持 Context、Judgment、Feedback 的联系：判断需要什么，为什么需要，怎样取得；人或后续结果能纠正什么；变化后哪些判断需要重做。重要未知留在对应 Decision 的 Knowledge Gaps，当前资料缺失、能力不足与授权事项则按实际责任承接。

验证时按 [行为验证](references/evaluation-learning.md) 先确定评价依据和允许的结果范围，再使用未参与提取的案例、独立复核或可核验结果。作者自检只支持自检结论；同一 Agent 生成方法、案例和预期后自评通过，不能构成独立验证。必要顺序、交接与恢复进入工作骨架；复杂设计过程和完整轨迹留在作者侧材料。来源不充分时，可以交付有限方法、未决 Gap 或目前不改 OM 的结论。

最终交付成果可以作为作者侧对照材料，用于定位判断差异、寻找证据线索和生成改进候选。区分当时可获得的业务输入与事后才有的结论或依据。写入运行时 OM 的方法必须能在工作尚未完成时，用当时可获得的资料、工具和协作执行。验证时先让执行者仅使用这些输入形成结果，再由作者侧对照最终成果；已见过对照答案的执行如实记录为同案对照。

## 工作规模与效率验证

处理大量判断项时，检查工作类型 OM 是否按共享事实和判断依赖组织推进。先识别决定分支的配置或任务条件，再围绕共同对象集中取证；让一份资料、一次回应或一次检查支持范围相容的多个判断，各项保留独立接受条件与依据。已有上下文和支撑充分时形成可用结果，剩余决定性未知按回答者合并承接，继续不依赖它的工作。具体分组、保存和接续方式放入工作类型 OM，作为可调整的方法。

评价效率时同时观察形成结果的速度、人工投入与判断质量。结合任务规模记录有依据的结果及正式完成范围、人工回应轮次、重复提问或取证、资料和回应的复用范围，以及补证是否改变结论或解除依赖。已开始项、草稿和工具调用数只说明活动量；比较方法前后时保留输入范围、难度、模型与工具、人工协助及等待时间的差异，避免将提前排除、漏评或降低接受尺度误判为效率收益。

先选一个后续工作片段观察候选方法：记录起始输入和未决依赖，检查分组是否减少重复协作、是否更快形成可核验结果，以及是否仍逐项满足判据与强制过程。复盘只保留解释收益或偏差所需的记录。证据暂不足时标明待观察，再按真实执行反馈调整，不将一次提速视为普遍验证通过。

## 反馈、学习与采用

先判断反馈改动了什么、改到什么程度、适用于哪里。将回应与前一轮判断对照，识别它是在纠正事实、限定触发条件或范围、调整确定性、提出候选解释，还是明确改变决定。按回应实际覆盖的范围更新，保留其余仍有依据的判断；保留「我觉得」「可能」等表达的确定性，不能将局部修正扩大成对整项判断的替换。

再区分本案更新与可复用知识。一次反馈可以同时支持两种产物：将可迁移的判断方法及其触发条件提炼为 OM 改进候选，将对本案的具体解释按原有确定性、对象与适用范围记录。候选解释经核实后才作为本案结论；方法的推广另用对照案例检验。

人工观察和专业结论可以成为判断支撑，不统一要求附件、完整推理或另行独立复验；具体充分性及强制过程仍按适用要求判断。记录实际提供者、提交/转录来源和适用范围，未知理由保留未知，Agent 分析不冒充原结论。已有判断直接回传，待执行工作另行承接；部分回应只推进明确覆盖范围。

人工反馈先用于当前任务的有效处理：核对对象、版本、权限和适用范围，重新判断受影响部分，再通过业务能力执行和确认效果。记录依据与结果，不把一次接受等同于普遍正确。

反思重建当时可见知识、事实、动作、人工介入和结果，比较知识缺失、上下文获取、能力合同、交互与执行偏差等解释。学习候选、候选修订、验证结果与正式采用分别保留证据。采用遵循已有授权与宿主治理；不增加重复审批，也不把未采用的候选写成权威方法。

本 Skill 的文档契约属于作者侧方法，不证明宿主已经具有 Context Compiler、自动案例采集、Decision Queue、ID 解析或发布能力。缺能力时说明依赖和可用替代路径；不要以文案制造已实现能力。

## 交付

按用户范围交付评审、候选知识文件或最小修订，说明依据、适用范围、知识缺口、实际验证强度和采用状态。需要文件时沿用宿主目录与版本约定；新包可参考知识对象契约。

评估价值时关注判断质量、上下文可取得性、后续案例迁移、专家理解与反馈成本，以及已有正确行为是否保持。文件完整、一次成功或更像专家的措辞都不能证明方法稳定。真实业务写入、历史资料使用和外部调用继续遵守已有授权，不自动重放任务。
