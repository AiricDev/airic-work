# 工作骨架、交接与恢复

用于设计必要工作依赖与责任接续。工作环节按交付和协作组织，Decision 按判断知识组织，两种粒度可以不同。它们都不直接规定宿主后台任务、事务或数据库对象。

## 检验工作边界

以“一项可交付或交接的业务义务”为起点，检查独立价值、部分完成、中断接续和重复覆盖。只为取得同一判断进行的多次查询可以合并；可独立交付、分别等待或由不同责任方承接的义务可考虑拆分。

| 内容 | 应回答的问题 |
| --- | --- |
| 目标与范围 | 谁需要什么结果，覆盖哪些业务对象，何时完成或可以明确等待？ |
| 触发与依赖 | 哪些事件、输入、已有工作或判断使它成为下一步？哪些顺序有业务/安全等强制依据，来源与履行证据是什么？ |
| Decisions | 需要哪些判断，怎样路由，缺少事实/知识/权限时由谁承接？ |
| 行动与效果 | Agent 和人各做什么，通过哪个实际能力，如何确认结果？ |
| 交付与引用 | 产物是否可用、可定位、可解释覆盖范围，是否支持另一执行者接续？ |
| 反馈与恢复 | 收到什么信息后重判哪些部分，部分/冲突回传和要求变化如何处理？ |

一个环节只有“分析一下”时需要澄清用途和产物；多个环节重复取得同一结果时可共享工作并保留覆盖关系。拆分依据是实际业务和协作价值，不追求唯一最佳层级。

按 [方法推导](derivation-method.md) 区分 Mandatory How 与 Discretionary How：工作骨架保留必要依赖、强制过程和协作恢复；建议路径允许 Agent 在目标、判据和权限内替换。结果质量与强制过程履行分别核验。

## 贯通一次真实往返

用业务系统已有语义说明：

1. **发起**：已知事实、具体缺口、影响、承接者、所需交付以及关联原义务的引用。
2. **承接与等待**：实际通知/登记机制，等待期间可继续的独立工作。
3. **回传**：结果、来源、对象和版本；无法匹配先澄清。
4. **核验**：是否回答原问题，覆盖哪些对象/工况，是否矛盾、过期或仍有缺口。
5. **恢复**：重判受新事实影响的部分，处理原事项和剩余义务，确认实际效果。

换位扮演发起者、承接者和恢复者，检查各自是否知道下一步。再选与当前范围相关的部分回传、对象不符、范围变化或响应丢失变体，修订断点。

发送请求、文件上传、任务完成、专业接受和知识采用是不同事实。使用持久业务记录/轨迹定位，不依赖完整聊天记忆。中断后先核对业务效果和回执，再按实际幂等与冲突合同恢复或重试。

## 责任边界

业务系统维护权威状态、授权、事务和版本约束；运行宿主维护实际执行与请求记录。OM 描述判断和必要协作依赖。缺少接口、通知、上传或关联入口时，指出可用替代和能力缺口，不能用更多指令假装存在。

专业判断的人工反馈按 [反馈与案例](feedback-and-cases.md) 准备 Brief、记录实际理由与范围；工作恢复不等待所有反馈都成为正式知识。
