# OME 作者侧知识对象契约 v0.5

这些契约表达知识语义，不规定 Airic Work 的数据库、API、Context Compiler 或状态机。沿用已有路径、ID、版本和加载机制；缺少自动解析时提供实际可访问的链接。只建立对当前任务有用的文件。

本版补充评价与过程约束的语义，沿用已有 Section、路径、ID 和 Gap 生命周期；不要求新增强制字段或迁移既有 Schema。Acceptance / Evaluation Criteria 可放在现有 Judgment / Judgment Basis / Method 中，以需要的详细程度表达。

## 对象关系与存放

| 对象 | 职责 |
| --- | --- |
| Root OM | 常驻工作体系入口：范围、应用对接、工作类型、知识架构、路由、加载与公共约束 |
| 工作类型 / Workflow OM | 某类工作的目标、输入、产出、必要工作依赖、协作恢复与所需知识的路由 |
| Decision Model | 可复用的判断问题及其上下文、方法、边界、案例、反馈和验证 |
| Subject Knowledge | 可共享的标准、概念、专业知识；说明来源、版本和适用范围 |
| Decision Episode | 一次实际判断的情境、依据、行为、人工反馈及结果的证据组织 |
| Precedent / Judgment Case | 经审阅采用、面向明确 Decision 用途的案例解读及其证据关联，包含迁移边界 |
| Test Case | 作者侧验证资产：检验方法的场景、预期和禁止推断；实际运行结果另作引用 |

Episode、Case 等首先是内容语义；可以引用宿主已有记录或用 Markdown 表达，不要求各建独立存储对象。同一事件可支持不同 Decision 的不同案例解读。运行证据保留在实际记录中，案例和方法通过引用关联，避免形成第二本业务账。

沿用现有入口；独立 OM 仓库可以直接以根 `om.md` 起步，嵌入式包可使用 `operating-models/<scope>/om.md`。按实际范围建立 `work-types/`、`decisions/` 和 `knowledge/`。已采用且用于运行时的最小案例解读可内联于对应 Decision，或放 `decisions/<id>/precedents/`；全局 `precedents/` 用于确实独立共享的案例知识，不是所有案例的强制位置。

OM 正式目录按运行时用途组织。构造用 Work Map、访谈、样例来源/案例底稿、未采用的候选解读、Patch 与完整验证记录集中在 `.ome/`；验证与回归场景放 `.ome/tests/`，案例底稿可放 `.ome/cases/`。它们可长期维护并进入 Git，属于作者资产。已有路径按宿主约定维护；用户要求统一作者边界时，迁移材料并闭合引用，不保留重复的运行时入口。

Root 常驻，其他知识按当前判断逐步加载；业务执行不读取作者工作区，也不因审计或来源链接自动扩读研究资料。Decision 保留影响实际使用的来源/版本、知识缺口和简要验证状态；详细验证证据由作者入口关联。标准正文及其权威、版本与覆盖限制属于运行时 Subject Knowledge。

案例按用途判断：研究/验证材料保留作者侧；经审阅采用、当前判断确需借鉴的最小解读才进入 Decision 的 Precedent，保留关键事实、理由、迁移边界与必要的稳定证据引用。避免要求执行者加载完整案例包才能使用规则。这些路径约定不自动实现宿主加载排除、权限、Git 忽略或发布能力。

## Root OM

入口应让执行者知道在什么业务体系中工作、怎样选择工作类型、在哪里取得上下文与方法，以及公共约束是什么。按常驻方法上下文编写，可由宿主将明确版本装配进 system prompt 或等效指令上下文。Root 可以只路由到工作类型或子 OM，没有直接 Decision 也是有效结构。

Root 的范围可以是单类工作、一个应用的多类工作或跨应用协作；不预设一个 App 对应一个 OM。按当前范围考虑以下职责，简单场景可合并表达：

| 职责 | 应说明什么 |
| --- | --- |
| Purpose & Scope | 服务对象、业务用途、支持范围和责任边界 |
| Application Integration | 对接应用、关键业务对象与语义、权威事实来源、上下文入口、能力/操作 Skill 与接口合同的可访问引用 |
| Work Types | 工作分类、目标、触发线索、输入、可用产出、方法入口；歧义或不支持的请求怎样处理 |
| Knowledge Architecture | 工作类型、Workflow、子 OM、Decision、共享知识和案例的责任与依赖；规模需要时引用 architecture-map |
| Routing & Loading | 如何从任务及实际上下文选择工作类型，再取得具体方法和知识；常驻与按需内容、版本及入口不可达时的处理 |
| Shared Operating Principles | 跨工作类型的公共约束、业务状态权威、协作、反馈与必要恢复约定 |

应用对接保留指导工作所需的语义，具体操作方法、API Schema、权限校验和回执规则引用实际 Skill/合同，不重复维护。知识架构图面向工作和知识导航，不要求复制应用代码架构。工作类型与 Workflow 不强制一一对应，分类不直接定义 Runtime Task 或状态机。

```markdown
# <工作体系或工作范围>

## Purpose and Scope
<服务什么业务用途；适用范围与责任边界>

## Application Integration
<应用与关键业务对象；权威来源、上下文和能力入口；引用 Skill/接口合同>

## Work Types
| 工作类型 / 触发线索 | 目标、输入与产出 | 方法入口 / 版本 |
| --- | --- | --- |
| <类型或条件> | <用途和边界> | <工作类型 OM、Workflow 或其他实际入口> |

## Knowledge Architecture and Routing
<知识地图或引用；路由条件、依赖、常驻/按需内容、版本与入口异常处理>

## Shared Operating Principles
<公共约束、事实与状态权威、协作及反馈约定>

## Validation
<验证范围与证据；仍未覆盖的部分>
```

工作类型/Workflow 子 OM 在实际需要时展开目标、完成条件、工作骨架、输入与产出、Decision/知识路由、交接和恢复。已有 Work Definition 可承载这些语义，无需另建同义入口。不要仅因工作有多个阶段就机械新增工作类型。

小包可以直接在 Root 定位具体 Decision。Root 保持足以开始工作的说明和导航，详细 Judgment 留在 Decision；不默认加载全部知识。目录不产生继承，使用、特化和组合需显式引用并说明条件及冲突处理。

## Decision Model

以下是需要考虑的语义，按实际复杂度合并章节，不要求每个 Decision 填满一张表。省略会影响执行的内容时，说明缺口和影响。元数据沿用宿主；新文件可使用少量稳定的 `id`、`version` 和 `status`，运行版本以实际提交/采用记录为准。

| 内容 | 应表达什么 |
| --- | --- |
| Question / Objective | 需要判断什么，结果供谁做什么；目标、风险与成本范围，不能只是“综合分析” |
| Trigger / Applicability | 什么线索使它值得考虑，以及适用对象、条件、排除范围和规则版本 |
| Constraints | 不可越过的专业约束、公共规则引用、授权/专业签署边界；Mandatory How 的来源、版本、适用条件、履行证据和例外权限 |
| Context Dependencies | 每项依赖的判断作用、必需条件、充分性、来源/权威/版本、获取与异常处理 |
| Judgment Basis / Method | 专业依据、Acceptance / Evaluation Criteria、关键区分、比较与权衡、诊断/优先级、不确定性、例外、接受/停止或升级条件；区分建议做法，保留适当裁量 |
| Outcomes | 可支持的结论及范围、候选选择/排序、诊断与不确定性、有限交付、未决情形、继续改进或交接；与最终业务签署状态分别说明 |
| Knowledge Gaps | 尚缺的持久性知识、影响、取得方式、解决证据与状态 |
| Precedents | 面向本 Decision 的案例解读或具体解读链接、使用目的、关联规则和迁移限制；没有案例时明确验证范围 |
| Feedback | 哪些信号可评价判断，谁提供、何时可得、什么变化要求复查，以及证据记录入口 |
| Validation | 运行时保留验证状态、适用范围、强度与未覆盖限制；详细场景、预期和验证证据由作者工作区维护 |

Trigger 与 Applicability 可以合写，但应能区分“何时考虑”与“适用于何种范围”。Feedback 描述评价方法和采集路径，实际反馈属于 Episode/运行记录。候选依据需标明，不能因写入模板而成为权威规则。

### 评价知识的最小表达

在既有 Section 中按需合并说明：

- **接受与拒绝**：下游用途需要哪些质量维度；哪些缺陷不可被其他优点抵消；判据来自规则、用户偏好、专家经验还是待验证假设。
- **比较与裁量**：什么条件改变候选选择、权衡或优先级；允许多个合理结果或保留分歧的范围。
- **Good Enough 与停止**：可接受的剩余缺陷/不确定性，继续改进的价值与风险、时间和成本；未满足条件而资源不足时的有限交付、未决或升级。
- **过程边界**：哪些 How 可由 Agent 替换，哪些是必须履行的过程要求；具体顺序与交接可引用工作骨架，避免重复规则。

这些语义不要求固定评分表、独立 Verifier 文件或 pass/fail 字段。可用专家评价锚点、比较依据、置信限制和反例表达；有可靠阈值时再采用量化标准。仅有成品质量证据，不能证明 Mandatory How 已被履行。

Context Dependencies 可使用：

```markdown
| Context | 判断作用 / 何时需要 | 充分性与来源 / 权威 / 版本 | 获取和核验 | 缺失 / 冲突 / 变化后重判 |
| --- | --- | --- | --- | --- |
| <依赖> | <关联区分/规则> | <要求> | <实际路径> | <处理与恢复> |
```

重要 Gap 留在对应 Decision，不另维护一份手工同步的知识真相。可用稳定的局部 Gap ID，记录问题、影响范围、候选方法、承接者/下一步、解决条件、证据与采用版本。未知责任人可标待确定。

沿用宿主状态；没有约定时可用 `open → proposed → validated → resolved` 表示作者侧知识补齐过程。候选不等于通过验证，通过验证不等于正式采用。解决需要关联实际采用的变化和证据；新反证出现时重开或关联后续 Gap。当前事实缺失、授权和能力缺口不混入此生命周期。

## Decision Episode 与 Precedent / Judgment Case

复用宿主的稳定引用和版本，不要求模型自行制造不可变证明。Episode 至少保留足以重建判断的内容，缺失信息按实际标记：

| 内容 | 记录要求 |
| --- | --- |
| Situation | 对象、目标、触发、范围和相关 Decision/OM 版本；新判断可暂时没有对应 Model |
| Context and Evidence | 当时实际可见的事实、来源和版本，重要缺失与假设 |
| Judgment and Action | Agent 建议、实际采用的判断/行动、人工干预及各自来源 |
| Rationale | 实际记录的理由；专家事后解释与 Agent 重建分别标记，未取得则保留未知 |
| Result and Feedback | 后续业务结果、独立评价、剩余不确定性及观察时间；未观察不得补写成功 |
| Provenance | 实际记录定位、作者/审阅来源、日期与版本，以及证据限制 |

### Decision 拥有案例解读

共享来源保留实际情境、证据、原有判断与理由、后续结果和来源限制，不能只剩背景。面向 Decision 的解读说明这段经历对当前判断问题有什么价值。每个解释关联来源及版本，并区分当时理由、事后专家解释和作者重建；后来的解释不覆盖或冒充原有理由。

解读经所需验证与现有审阅采用后形成 Precedent。内容包括 **Purpose / Interpretation / Boundary / Review and Adoption**：用于哪个 Decision/规则、哪些事实支持哪项关键区分、为什么接受/拒绝/偏好某个结果、证据支持到哪里、什么条件可迁移、什么变化使其失效、是否有反例，以及采用范围和记录。结果尚未知的专家判断可保留为有限案例，标明证据强度。正例、失败例和边界例均可提供价值，不把某次成功的 How 当成唯一允许路径。

以下为已经采用、运行时确需借鉴的解读的存放方式；未采用的候选解读与原始案例底稿保留作者工作区。按内容规模选择：

- 简短解读直接放 Decision 的 Precedents 部分，记录来源、使用目的、关键解读和迁移限制。
- 较长或较多解读放对应 Decision 的案例文件，便于按需读取；多个 Decision 可各自解读同一事件，公共事实通过来源引用共享。
- 确实跨 Decision 复用的完整解读可放全局 `precedents/`。每个引用说明本次用途和限制；不同视角复杂时可在共享案例中分节并引用具体章节，完整解释只在一处维护。

物理共享不代表所有 Decision 共享同一解释。可迁移的共享解读也应注明其适用的判断问题；独立存放不要求消除 Decision 视角。仅有事件背景、没有实际判断或判断价值的材料属于来源材料，不因目录名成为 Precedent。

真实记录、事后重建和合成示例需区分，必要时按案例片段标记混合来源。合成案例可用于教学或测试，不计入真实运行证据。保存的案例内容与“已经正确解释了因果”也需区分。

## Test Case 与过程材料

Test Case 沿用既有结构，表达关联 Decision/版本、场景类型、起始状态与输入、必要能力、允许结论/行动/产物、禁止推断和相关恢复条件。在这些内容中说明评价依据及来源、允许分歧、强制过程证据和停止/升级边界。用正反例、边界例、最小变化的对照案例检验区分；具体选择见 [行为验证](evaluation-learning.md)。

预期在观察运行前确定，实际结果另作引用，标明评价者/独立性、可观察证据、未覆盖范围和是否运行。沿用宿主的测试状态；若使用通过/失败，它表示本次测试相对预期的结果，不表示领域 Judgment 只有二元取值。部分支持、分歧和未知保留在结果说明中。合成用例、自检与独立验证分别标记。

Work Map、访谈、候选 Patch、Knowledge Delta 和验证报告使用最小可用形式。候选 Patch 连接观察、归因、目标 Decision/规则、预期变化、回归证据和采用状态。派生索引注明源版本，不能成为另一份需要手工维护的知识权威。
