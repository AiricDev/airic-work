# Feedback Discovery、Decision Brief 与案例采集

用于设计人工介入、发现学习信号，或从实际判断形成可复用案例。目标是在保持业务处理可靠的同时，降低人理解和反馈的成本。

## 在设计 Decision 时发现反馈

Decision 的 Outcomes 描述可能结论；Feedback 描述怎样评价实际判断。为当前范围寻找有区分力的反馈，不要求每个判断都有即时、客观的正确答案。

围绕代表案例问：

- 怎样知道判断有用、过宽、遗漏或不适用？预期业务效果和观察证据是什么？
- 什么算 good enough，哪些缺陷必须拒绝，两个可用结果怎样比较，继续改进到何时值得停止？这些标准来自谁、适用什么目标与风险？
- 谁能提供评价：领域专家、独立复核者、执行者，还是后续检验/业务结果？其权限与专业范围是什么？
- 什么时候可取得反馈，怎样关联原判断、对象、版本和范围？哪些效果尚不可观察？
- 什么新事实、分歧或结果会触发复查？缺少反馈会限制哪些可靠性结论？

人工选择、事实纠正、理由补充、专家分歧、重复求助、意外成功、例外和后续失败都可能提供信息。优先采集能改变理解的片段，避免只保存负面事件造成选择偏差。采集覆盖不足时，不将记录频率当作真实发生率。

人工决定对当前事项的处理效力遵循业务权限；其解释和可推广性需要证据与适用范围。区分事实纠正、规则要求、专业权衡和个人偏好，记录相应来源。专家之间的不同判断可以保留为待解释分歧，不通过多数票或职位自动推导通用知识。主观评价可借助正反例和边界锚点表达，仍需按 [行为验证](evaluation-learning.md) 检查迁移。

## 为人编译简洁的 Decision Brief

复用业务系统/宿主已有请求通道。没有正式 Request 工具时，可在授权的对话或工作记录中提供同样的内容，明确它具有何种实际效力。

Brief 先让人知道需要做什么，再提供足以评价的依据。按需要组织：

1. **待决问题与请求**：需要判断、补充事实、授权还是复核，影响什么工作。
2. **关键情境**：对象、范围、触发原因、当时版本；事实与假设分开。
3. **候选选择**：可用选项、Agent 建议及简短理由，接受/比较标准、不确定性、主要取舍与停止或继续的理由。
4. **关键支撑与输入**：实际使用的资料、人工观察/专业结论和业务记录的来源、定位与范围；哪些信息尚未数字化，需人直接给出什么；详细原文按需展开，缺失或冲突如实说明。
5. **回应后的影响**：哪些部分会重判/继续，哪些仍然等待；必要的有效性条件。

显而易见的小问题可以缩短，重大判断可以附详细材料。不要为了表格完整让人阅读与当前选择无关的历史。摘要不取代原始证据；取得不到原文时说明限制。

## 低成本取得实际判断与理由

先利用人已经给出的回答和工作记录，再追问会改变当前处理或未来复用的关键未知。允许人直接选择、纠正、补充证据或限定范围；不要求每次填写完整案例表。

Agent 可以整理一段供核对的摘要：实际选择是什么、基于什么条件、理由来源、适用于哪里、什么变化后应复查。记录已有明确内容无需再次审批；只有未表达清楚且会影响含义的部分才请人确认。未确认的模型解释不能署为人的理由。

人可以直接提供观察或专业结论，不必将现场信息全部数字化或上传附件。内容和适用对象/范围需清楚，理由、时间、条件与限制按实际已知程度记录；未记录的推理保留未知，不为了知识提取追问完整经过。适用业务或专业要求明确需要理由、记录或过程时仍需满足。

声明的原提供者、实际提交者与代录/Agent 转录分别归因；直接回应、代录和 Agent 分析不能互相冒充。照片可能只用于辅助说明，不把工程师判断归因为 Agent 已从照片独立核验。文字输入可按业务合同留存，文件先在宿主分析，需正式留存或资料引用时再登记业务修订。

分别识别回应内容：

| 回应类型 | 当前处理与潜在学习 |
| --- | --- |
| 新事实/证据 | 核验来源和覆盖范围，更新受影响判断；事实本身通常仍留在业务记录 |
| 专业判断/纠正 | 记录实际选择、可取得的理由和边界，作为案例与知识候选 |
| 授权/例外批准 | 检查业务权限和有效范围；不能直接推导专业方法普遍正确 |
| 目标/偏好变化 | 明确目标或约束变化造成的选择，避免错归因为原规则错误 |
| 分歧/理由缺失 | 保留未知与各方证据，需要时继续调查，避免编造共识 |

## 先处理当前事项，再提取可复用内容

收到回应后，核对请求、业务对象、上下文版本、范围和权限是否仍有效。已过期或冲突的回应按实际合同处理。重新判断受影响部分，通过受控业务 API/MCP 执行并核对回执；上传、同意、业务写入和专业接受分别按合同解释。

已有观察或判断可直接回传，不补造测试/检查任务；尚未开展的工作才需要承接和交付。部分回应逐项说明覆盖与剩余问题，只推进明确满足的等待；回应记录、工作完成、结论采用和最终确认分别处理。后续补充或更正关联原回应/业务记录并保留历史，重判受影响范围。

将回应与实际执行、剩余缺口和后续结果关联成 Decision Episode。优先引用已有持久记录；等待期间和反馈后，不受影响的工作可在授权范围内继续。案例记录不替代业务状态。

反思时提取候选区分、方法、例外或边界，也可能得出仅适用于本案、需要补证或应改工具的结论。候选迁移到相邻案例前，检查对象、目标、依据版本、决定性条件和权威范围是否相容。

确定案例面向哪个 Decision/规则，再提取其判断用途、支持它的事实与理由、反例和迁移边界。同一 Episode 可产生不同 Decision 的不同解读，共享实际来源，不复制完整经过，也不把重建理由署为当时理由。没有对应 Decision 时先保留候选用途，不能强行归入不相干判断。

依据 [验证与学习](evaluation-learning.md) 完成所需验证，并遵循实际人工审阅/采用机制。正式案例使用 [对象契约](artifact-contracts.md) 的 Precedent 语义：简短解读内联，较长内容放对应 Decision 的案例文件，确实共享的解读独立维护并注明引用目的。不必新增与 Precedent 重复维护的 Judgment Case 系统。

## 观察反馈方法本身

结合判断质量观察：人重建上下文的时间、补问次数、有效回应比例、记录理由的负担、反馈后恢复情况，以及后续是否反复纠正相同问题。Brief 更长、记录更多或求助更少，都不能单独证明改进；求助减少也可能来自遗漏升级。

对不能客观判定的专业判断，保留评价者、理由、分歧与后续修订能力。反馈设计的目标是取得有信息量的证据，并让修正易于发生。
