# 从案例发现和构造判断知识

用于创建候选 OM、实质调整知识组织或发现尚未建模的专业判断。以下是可往返的设计动作；小范围改进只使用相关部分。

## 阶段与持续产出

沿用同一组 Git / Markdown 知识对象；每阶段直接更新有用内容，后续持续细化，不为阶段另建一套正式 Schema。

| Phase | 方法重点 | 本阶段的具体产出 / 完成依据 |
| --- | --- | --- |
| 1 Work Scoping | 整体地图、用途、目标、风险与成本范围 | 最小 Root OM / Work Map，能说明谁用什么成果完成什么工作 |
| 2 Decision Discovery | Evaluation Decomposition，再核对过程热点 | 候选问题与路由；每个问题有评价用途、关键区分和未知 |
| 3 Context Dependency Analysis | 从判据反查必要上下文与权威来源 | Decision 的依赖及 Gap；关键依据有获取路径或明确限制 |
| 4 Knowledge Elicitation | 用正反例、边界与对照提取 Judgment | 判断依据、接受/比较/停止条件、Precedent 候选与待解 Gap |
| 5 OM Construction | 整理知识归属、裁量空间与必要工作骨架 | 可达的候选知识包；强制过程有来源，建议做法与规则可区分 |
| 6 Validation | 按预先确定的判据与独立证据检验迁移 | Test Case、实际验证记录、未覆盖范围和必要修订 |
| 7 Reflection & Evolution | 需要实践归因时按需使用既有反思模块 | 有证据的改进候选、回归与采用记录；依 [验证与学习](evaluation-learning.md) 接续 |

这些是作者侧阶段，允许往返或局部进入；不定义后台执行的生命周期。Phase 7 的实践提取与归因沿用已有模块，不在 Decision Discovery 中重做一套反思流程。

## 先建立最小整体地图

创建或实质重构 OM 时，先按 [Root OM 契约](artifact-contracts.md) 明确整体范围、应用对接、工作类型、知识组织、路由与加载方式，形成可常驻使用的入口。Root 可以没有直接 Decision；只支持一类工作时保持简单，多类工作时先建立可区分的入口。

地图足以让执行者从真实任务找到工作方法即可，不要求先穷尽全部 Workflow 或知识目录。规模需要时把工作责任、模块依赖、上下文来源与知识入口展开为 architecture-map，Root 保留摘要与引用；避免重复维护同一张地图。

从真实请求检查工作分类：目标、输入、产出和完成条件是否有独立意义？某个阶段、等待或恢复究竟是既有工作的路径，还是独立工作类型？未决边界明确标记，不因目录划分创建新的业务对象或 Runtime 状态。

局部改进复用现有地图，只核对受影响路由。案例中发现新的工作类型、依赖或错误路由时回头修正地图；整体组织和具体 Decision 相互校准。

## 选择工作类型，从工作用途定位案例范围

在所选工作类型中，写清当前输入、业务义务、执行者、下游使用者，以及“谁依据什么产物能做什么”。记录目标、可接受风险、时间/成本约束和评价者；目标或偏好尚不明确时先标记，不替用户编造。用一个看似完成但不可使用的结果检验完成条件。保留最小的必要工作骨架，标出产物、判断、外部等待和恢复入口；工作粒度参见 [工作骨架](work-unit.md)。

区分材料的证明范围：成果说明需要什么；轨迹说明发生过什么；专家陈述提供理由和经验；模型知识提出候选解释；业务合同界定实际能力。只有成果时可重建候选过程，明确未知，不能把它写成历史事实。

## Decision Discovery：先做 Evaluation Decomposition

从结果及其用途反推需要哪些判断，尤其适用于写作、设计等没有明显操作分支的工作。先对照可用与不可用的成果，再回看过程中哪些知识造成差别：

| 评价问题 | 要分解的专业内容 | 候选 Decision 的问法 |
| --- | --- | --- |
| 什么算 good enough？ | 必须满足的用途、质量维度、可接受范围与剩余不确定性 | 当前结果在什么范围内可被谁使用？ |
| 何时拒绝结果？ | 不能被优点抵消的缺陷、风险、证据不足或过程违规 | 哪些缺陷必须修复，哪些结论必须保留未决？ |
| 怎样比较候选方案？ | 各维度取舍、偏好来源、优先关系与无法直接比较的情况 | 在当前目标和风险下为何选 A、选 B 或保留多案？ |
| 何时停止改进？ | 已满足的接受条件、剩余缺陷、额外改进的价值与成本 | 应交付、继续、限缩范围，还是升级处理？ |

不要把评价维度、每条检查项或每次润色机械变成独立 Decision。沿用下文的聚合粒度检查：哪些区分需要共享的专业依据、上下文和例外，哪些只是确定性校验或通用执行能力？已有 Workflow 可以补充过程线索，但不必先写完整 SOP 才能发现判断。

### Verifier 视角与判断形态

问“什么证据或评价可以支持、质疑这项判断”，有助于发现 Decision，也有助于设计测试。Verifier 可以表达接受标准、候选排序、风险权衡、诊断支持度、优先级依据、不确定范围或升级条件；不是所有判断都能压成 pass/fail。诊断时还要保留竞争解释和可区分它们的证据；多个候选可能都可接受，权重也未必可量化。

评价需有来源和适用范围：权威规则、用户目标/偏好、专家判断、经验性启发或待验证假设分别标记。主观标准可通过正反例、锚点和有理由的评价外显；不能因难以量化就忽略，也不能让生成 Agent 的偏好成为默认权威。详见 [行为验证](evaluation-learning.md)。

### Good Enough：接受与停止分别说明

围绕当前用途建立最小充分的评价约定：哪些维度必须满足，哪些允许权衡，什么风险或不确定性仍可接受，剩余缺陷由谁承担。不要为了便于测试虚构统一分数、精确阈值或固定改进轮数。

据此区分：已达到接受条件且继续改进的预期收益不值得成本，可以停止交付；虽有改进空间但风险可控，可以限范围交付并说明限制；关键条件未满足，应继续、补证或交给有权者处理。资源耗尽可以结束本轮尝试，但不能把不合格结果改称 good enough。目标、受众、风险或成本变化时需重判。

接受标准和停止规则分别落在既有 Objective、Constraints、Judgment、Outcomes 与 Validation 中，具体映射见 [知识对象契约](artifact-contracts.md)。

### 再沿案例寻找 Knowledge Hotspots

沿真实案例观察哪些区分改变了结论、行动、证据需求、可接受风险或适用范围。线索包括：

- 专家反复纠正、明显犹豫或与其他专家意见不一致的位置。
- 看似相同的输入产生不同处置，以及需要经验识别的例外。
- 专家认为“显然如此”，但新人或 Agent 经常误解的判断。
- 是否适用、证据是否足够、何时停止、何时升级、如何平衡冲突目标等隐含判断。
- 已有方法被绕过、额外调查改变了结论，或一次成功暴露了新的适用条件。

没有动作分支也可能有判断，例如决定哪些结论在现有证据下成立。一个复杂步骤则可能主要需要确定性程序或通用能力。不要用耗时长、工具多或章节名直接定义 Decision。

将候选写成问题，例如“当前证据足以支持什么范围的结论？”或“两个可用草稿在当前受众与篇幅下应怎样选择？”；同时记录触发线索、结果用途、评价依据、现有知识和未知。候选清单可放过程材料，不必先为每个问题建立正式文件。

按业务影响、复用机会、当前错误/人工负担和知识可提取性选择研究重点。频率只有记录覆盖明确时才可比较；不要制造精确分数。高影响且缺乏反馈的判断也可能值得优先研究。

## 检验 Decision 的知识聚合粒度

聚合围绕一个可辨识、可迁移的判断问题。比较候选时检查：

| 检查 | 聚合或拆分的依据 |
| --- | --- |
| 问题和用途 | 能否解释为同一个判断问题及相近结果用途？不同问题可组合，避免写成无限扩张的“综合评估” |
| 决定性条件 | 规则是否共同解释一组关键区分？仅为取得同一判断而查询多次，通常无需拆分 |
| 依据与适用范围 | 依据、权威来源或例外边界明显不同，可拆分或通过特化引用 |
| 演化与复用 | 一组知识能否在其他环节共同复用？修改一个部分是否总迫使无关内容一起变更？ |
| 可验证性 | 是否能构造具体输入、允许结论与相邻反例？问题过宽时收窄 |

这些是判断标准，不保证唯一划分。必要时保留两个候选方案，用真实案例比较路由、理解和维护成本。

一个 Decision 可以包含多条紧密相关的规则；不同 Decision 可以共享 Subject Knowledge、案例来源和有明确适用范围的案例解读。对同一事件，分别提取各 Decision 关注的事实、判断价值与迁移边界，避免把事实相同当成解读相同。物理文件数量不决定语义粒度。Decision 的触发条件也不决定后台任务创建或事务边界。

## Knowledge Elicitation：提取判据与专业 Judgment

先提出带来源状态的候选判据和解释，让专家修正具体内容。优先问“为什么可接受、什么差别会改变判断”，再了解确有必要的做法。围绕一个真实判断少量提问，避免要求专家从空白讲完整 SOP。

| 提取动作 | 可用问题或练习 | 需要得到的内容 |
| --- | --- | --- |
| 重建关键线索 | 你最先注意到什么？哪项信息让你排除其他解释？ | 注意线索及其判断作用 |
| 正反例锚定 | 哪个成果可用，哪个看似不错却必须拒绝？为什么？ | 接受标准、不可抵消的缺陷与来源 |
| 对比案例 | 相似目标下为什么这次选 A、另一次选 B？ | 决定性条件与适用边界 |
| 反事实 | 只改变这一条件，你还会作同样判断吗？ | 条件是否真正影响选择 |
| 边界例与充分性 | 这个勉强可用的结果差在哪里？再少什么就不能接受？ | 可接受范围、证据充分性与不确定性 |
| 比较与优先级 | 两个候选都可用时怎样选？先改哪个问题，代价是什么？ | 偏好、权衡、风险排序与不可比较情形 |
| 停止与预算 | 为什么此时交付？多做一步可能改善什么，是否值得？ | 接受与停止条件、有限交付和升级范围 |
| 追问例外与冲突 | 哪种情况下不该用此方法？两个依据冲突时怎样处理？ | 例外、优先关系和升级条件 |
| 检查过程必要性 | 换一种做法得到同样结果能否接受？什么要求禁止这样换？ | Discretionary How 与 Mandatory How 的边界 |
| 教给后继者 | 按这段候选方法判断一个未讨论过的相邻案例 | 发现表达遗漏和迁移失败 |

专家事后解释可能不完整，也可能是重新构造的理由。保留实际记录、专家解释与模型推断的差别。目标是可检查的判断依据和方法，不要求展示完整内部思维过程。标准阈值、项目事实和既有执行结果从相应权威来源核对。

候选方法可以保留启发式、权衡和专业裁量。记录哪些判断有共识，哪些取决于特定用户/专家偏好，哪些仍存在合理分歧。尚不能明文化的部分应具体标为 Gap 或需要专家协助的范围；不要用伪精确规则掩盖它。一次专家接受提供本案证据，不能单独建立通用判据。

### 区分 Discretionary How 与 Mandatory How

| 类型 | 如何识别 | 如何写入 OM |
| --- | --- | --- |
| Discretionary How | 多条路径能满足相同判据，未发现适用的强制过程要求 | Agent 在目标、风险和权限内自主选择；有价值的建议做法注明适用性，允许替换 |
| Mandatory How | 法务、合规、业务、安全或合同要求特定顺序、取证、独立复核、角色或留痕 | 在 Constraints 或工作骨架声明来源/版本、适用条件、必要动作/顺序、履行证据与例外权限 |

历史上一直这样做、专家个人习惯或单次成功路径，不足以证明 Mandatory。工具调用也可能受专业依据或合同约束，不能一概视为自由选择。要求来源未核实时保留待核实状态，按已有风险与授权规则处理，不自行宣布豁免。

模型能力增强后可以重新检验建议做法是否仍有增益；Mandatory How 的调整需由相应权威和既有治理机制承接。测试应同时容许满足要求的替代路径，并识别“结果看似正确但违反强制过程”的案例。

## Context Dependency Analysis：让依赖支撑判断

从每条关键区分反查“如果没有这项信息，哪些选择无法成立”。为必要依赖说明：

- **作用与条件**：影响哪项规则/区分，何时必需；缺失时仍能支持什么。
- **充分性与来源**：需要何种质量、覆盖范围、精度、权威及版本；来源位置是否只是线索，还是足以支持结论。
- **获取与核验**：实际可用入口、参数或业务引用，以及如何确认取到了正确对象和版本。
- **冲突与变化**：依据不一致如何处理；新事实、版本或范围变化后重判哪些部分。

区分规则知识、项目事实、证据、业务状态和能力依赖。公共依赖可在 Root OM 说明，Decision 补充具体作用。通用文件读取等宿主标准能力只在实际有特殊要求或缺口时声明。

当前事实缺失走取证路径；持久性判断知识不足进入 Decision Gap；缺工具或回传入口交给能力/产品责任方；授权要求引用实际合同。不能都交给知识补丁处理。

## 形成最小候选并检验

按 [知识对象契约](artifact-contracts.md) 将稳定判断内容写入 Decision，并核对 Root → 工作类型/Workflow → 所需知识的实际可达路径；简单包可以直接路由。共享专业知识与案例来源保留引用，案例解读归属相应 Decision 或明确共享位置，工作骨架保留必要依赖和恢复方式。未确认内容就地标明。

按 [反馈设计](feedback-and-cases.md) 发现判断的评价来源，准备简洁 Brief 和案例采集方式。用原案核对解释，再按 [行为验证](evaluation-learning.md) 留出未参与提取的案例，预先写下评价依据和允许结果，采用独立复核或可核验结果检验迁移。新例子需标明真实、重建或合成，不能冒充运行证据。

依照 [验证与学习](evaluation-learning.md) 记录实际验证强度。规则未加载先检查路由；输入取不到检查依赖和能力；动作正确但产物无用回到用途。允许结论是继续调查、收窄范围或保持原方法。
